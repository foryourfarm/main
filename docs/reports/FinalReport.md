## 1. `weather_API2` 재시도 결과 — 유효하지 않은 키다

`.env`에 추가해 주신 `weather_API2`를 config에 연결하고 재시도했습니다. **모든 API에서 401**입니다.

| 대상 API | 결과 |
|---|---|
| 농업기상 관측 V3 (`getWeatherMonDayList3`) | ❌ HTTP 401 Unauthorized |
| 농업기상 지점정보 (`getObsrSpotList`) | ❌ HTTP 401 |
| 농경지화학성 V2 (`getFarmExamPhInfo`) | ❌ HTTP 401 |
| 농업기상 10분·기간별 | ❌ HTTP 401 |

### 원인 진단 — 포털이 키를 인식하지 못한다

명세서 §공통 응답 코드에 `101`(서비스키 인증 실패)이 있는데, **그게 오지 않고 HTTP 401이 옵니다.** 둘의 의미가 다릅니다.

| 응답 | 의미 |
|---|---|
| `<result_Code>101</result_Code>` | 포털은 키를 알지만 이 API에 대한 권한이 없다(활용신청 미승인 등) |
| **HTTP 401 Unauthorized** (본문에 `result_Code` 없음) | 포털 게이트웨이가 **키 문자열 자체를 못 알아본다** |

대조군으로 검증했습니다:

```
정상 키              HTTP 200  result_Code=200
weather_API2         HTTP 401  result_Code=-     ← 아래 두 개와 동일
완전 쓰레기 키        HTTP 401  result_Code=-
정상 키 1글자만 변형  HTTP 401  result_Code=-
```

**`weather_API2`는 존재하지 않는 키와 완전히 같은 반응**입니다. 인코딩 문제도 아닙니다 — 기존 키와 동일하게 64자 순수 영숫자이고(`%`·`+`·`=` 없음), URL 인코딩/디코딩·raw 쿼리스트링 조립까지 시도했으나 전부 401입니다.

### 추정 원인과 확인 방법

1. **키 복사 누락/오타** — 길이는 64자로 맞지만 내용이 다를 수 있습니다. 포털의 **"일반 인증키(Decoding)"** 값을 다시 복사해 주세요.
2. **신규 발급 직후 전파 지연** — data.go.kr은 발급 후 반영에 시간이 걸립니다(통상 1시간 내). 시간이 지난 뒤 재시도해 볼 값이 있습니다.
3. **다른 포털 계정의 키** — 계정이 다르면 활용신청도 따로 필요합니다.

### 유효해지면 자동으로 쓰입니다

`weather_client._fetch_page`에 **키 폴백**을 넣었습니다. 쿼터 소진(`429`)·인증 실패(`401`/`403`/`101`)면 백오프로 버티지 않고 **즉시 다음 키로 전환**합니다(쿼터는 대기해도 풀리지 않으므로 기다리는 것이 낭비입니다). 빈 키는 후보에서 제외합니다.

```python
def _service_keys() -> list[str]:
    return [k for k in (settings.weather_api, settings.weather_api2) if k]
```

→ 키만 올바른 값으로 바꾸면 코드 수정 없이 동작합니다.

### 쿼터 현황 (보고 요청 사항)

**쿼터는 엔드포인트별로 따로 관리됩니다.**

| 엔드포인트 | 상태 |
|---|---|
| `getWeatherYearMonList3` (년도별 월) | 🔴 **소진** — 3회 시도 모두 429 |
| `getWeatherMonDayList3` (월별 일) | ✅ 정상 — 누적 70콜 이상, 429 없음 |
| `getWeatherTermDayList3` (기간별 일) | ✅ 정상 |
| `getObsrSpotList`, 흙토람, apihub | ✅ 정상 |

소진된 엔드포인트는 쓰지 않고 **일별을 받아 직접 집계**하도록 구현했습니다. 추가로 ETL에 **캐시**를 넣어 재실행 시 API를 아예 부르지 않습니다(`--refresh`로만 재조회).

## 2. `climatology_service.py` 점검 결과

코드를 읽는 것으로 끝내지 않고 **256개 구역 전체를 실행**해 검증했습니다.

### 2.1 잘 동작하는 것

```
256개 구역 전체 실행: 0.96초 (구역당 3.8ms)
  자체 평년치 보유   116개
  인접 지역 대체     140개   ← 전 구역이 12개월 값을 받는다
  평년치 없음          0개
결정론: 같은 입력 2회 → 대체 출처·일조값 완전 동일 ✅
```

- **대체 로직이 의도대로 동작**합니다. 예: 고창군 → `"이 지역 평년치가 없어 가장 가까운 장성군(약 16km) 평년치로 대체했습니다"` — §1-4 한계 표기가 실제로 사용자에게 전달됩니다.
- **결정론 보장** — 동거리 후보는 `region_id` 작은 쪽으로 고정(§2).
- 구역당 3.8ms로 성능 문제 없음(월별 재조회 없이 1~4쿼리).

### 2.2 발견해 수정한 결함 — 대체 출처가 일사량을 갖고 있지 않았다

초기 상태에서 **50개 구역이 일조 0개월**이었고, 그중 30개는 대체 출처(`고양시덕양구`)가 일사량 데이터를 갖고 있지 않아서였습니다.

근본 원인은 ETL이었습니다. 구역에 지점을 배정할 때 **"최근접"** 을 골랐는데, 마스터에 지점이 있어도 그 지점의 일사량 관측이 없는 경우가 있었습니다:

```
완도군   ← 배정지점 완도군 완도읍 (7.1km) / 적재된 월 0
파주시   ← 배정지점 파주시 아동동 (5.0km) / 적재된 월 0
가평군   ← 배정지점 가평군 가평읍 (0.0km) / 적재된 월 0
   … 116개 중 20개가 이렇게 비었고, 이 20개가 다른 30개의 대체 출처였다
```

→ `station_service.resolve_station()`에 `allowed_codes` 파라미터를 추가해 **"쓸 수 있는 것 중 최근접"** 을 고르도록 했습니다. ETL은 실제로 데이터가 있는 지점 집합(177개)을 넘깁니다.

**수정 효과 (256개 구역 재검증)**

| | 수정 전 | 수정 후 |
|---|---|---|
| 일사량 적재 | 1,129행 / 96구역 | **1,363행 / 116구역** |
| 일조 12개월 구역 | 202 | **232** |
| 일조 0개월 구역 | **50** | **0** |
| 구역당 평균 일조 월수 | 9.6 / 12 | **11.8 / 12** |

평년치를 보유한 116개 구역 전부가 일사량을 갖게 되어, 대체 출처가 비어 있던 문제가 연쇄적으로 해소됐습니다. 차용 구역은 90개(최대 31.6km)로 늘었지만 이는 "가까운 빈 지점" 대신 "조금 먼 실제 데이터"를 택한 결과이며 거리는 UI에 표기됩니다.

### 2.4 남은 한계 (설계상 허용)

- 대체 시 **위도는 공여 구역 기준**입니다. 평년치 값이 공여 구역 것이므로 일관되며, 위도 민감도가 낮아(0.5° 오차 → 일조 7분 미만) 실질 영향이 없습니다.

## 3. 🔴 테스트 전 반드시 해결해야 할 것

### 3.1 최우선 — 일조 지표가 점수에 반영되지 않는다

**일조 파이프라인은 완성됐지만 마지막 연결이 빠져 있습니다.**

```
일사량 API → 품질 필터 → 평년값 적재 → 일조 환산(R²=0.903) → sunlight_by_month ✅
                                                                      ↓
                                          crop_growth_guide에 'sunlight' 지침 ❌ 없음
                                                                      ↓
                                                       적합도 점수에 미반영
```

`calculate_suitability()`는 **지침(`guides`)을 순회**하므로, 지침이 없는 지표는 `breakdown`에 들어가지도 않고 가중평균에도 빠집니다. 실측 확인:

```
[일별 적합도] score=76.4 grade=A status=ok
  일조: None            ← breakdown에 sunlight 항목 자체가 없다
```

현재 `crop_growth_guide`의 지표 분포:

| 지표 | 건수 | 작물 |
|---|---|---|
| `temp_day` | 8 | 1,2,3,4,5 |
| `rainfall_daily` | 5 | 1,2,3,4,5 |
| `ph` | 2 | 1,2 |
| `temp_night_min` | 2 | 1,4 |
| `organic` | 1 | 1 |
| `p2o5` | 1 | 1 |
| **`sunlight`** | **0** | — |

**제가 임의로 채우지 않았습니다.** 농업 기준값은 시드 데이터로만 관리해야 하고(§18-2 하드코딩 금지) 추측이 금지돼 있습니다(§3.4). 작물별 일조 요구량(예: 사과 연 1,600시간 이상 / 상추 반음지 허용)은 **농업 문헌 근거가 있어야** 합니다.

필요한 것: 5종 작물 × 생육단계별 일조시간 최적/허용 범위 + 출처. 확보되면 `crop_growth_guide`에 마이그레이션/시드로 넣으면 즉시 채점에 반영됩니다(코드 변경 불필요).

### 3.2 생육 지침 자체가 희박하다

```
crop=3(오이): 2건    crop=5(상추): 2건    crop=2(배): 3건
```

오이·상추는 **지표 2개(기온·강수)로만 적합도가 산출**됩니다. 점수가 나오긴 하지만 "적합도"라 부르기엔 근거가 얇습니다. 테스트 시 이 점을 인지해야 하며, §15 QA 체크리스트의 "5종 작물 각각에서 정상 동작"은 형식적으로는 통과하지만 실질적으로는 미달입니다.

### 4.3 `weather_client.py` 완성 — 실측으로 두 결함 수정

**① 명세서 날짜 형식 오류.** 기간 조회가 `201`로 실패하던 원인입니다.

| 요청 | 결과 |
|---|---|
| `begin_Date=20240701` (명세서 표기) | ❌ `201 요청변수 형식 불일치` |
| `begin_Date=2024-07-01` | ✅ `200 정상` |

**② 페이지네이션 부재로 데이터가 조용히 잘렸습니다.** `Page_Size=100` → `rcdcnt=100`인데 `total_Count=6551`입니다. 기존 구현은 `Page_Size=9999` 한 방이라 우연히 통했을 뿐이며, 지점이 늘거나 기간이 길어지면 말없이 사라집니다. 순회를 넣어 `page_size=500`으로도 6,551행 전부 수집되며, 무한 루프 방지 상한(`MAX_PAGES=50`)을 뒀습니다.

### 4.4 `VWORLD_APIkey` 로드 실패 수정

`.env`는 `VWORLD_APIkey`인데 config 필드가 `vworld_api`였습니다 — 대소문자는 무시되지만 `key` 접미사가 달라 매칭 실패였습니다. 헤더 대소문자 버그와 같은 계열(조용히 빈 값)입니다. **8개 키 전부 로드**됩니다.

**부분적으로 가능합니다.**

| 기능 | 테스트 가능 여부 |

| 로그인·회원가입·인증 게이팅 | ✅ 가능 |

| 장기 탭(적합도·히트맵) | ⚠️ 동작하지만 **일조 지표 미반영**, 오이·상추는 지표 2개뿐 |
| 단기 탭(실시간 기상) | ⚠️ 미검증 — `weather_forecast_api` 경로 별도 확인 필요 |
| 챗봇 | ❌ 불가 (Ollama 미실행) |
| 프론트엔드 전체 | ❌ 불가 (`npm install` 필요) |

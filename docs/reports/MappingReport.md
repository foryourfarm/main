## 1. 먼저 인정할 것

지적의 핵심은 맞다. 세 가지를 잘못했다.

1. **지운 뒤 남긴 메모가 요구사항을 지웠다.** `Bug_Report.md`에 "관측지점 510개 시드 필요"라고 한 줄로 적었는데, 어려운 부분은 **목록**이 아니라 **배정**이다. 실제 과제(관측망 식별 → 좌표 확보 → 배정 → 미커버 대체 → 다중 지점 집계)가 그 한 줄에 전부 뭉개졌다. 부분 구현을 지울 때는 구현이 아니라 **요구사항**을 먼저 옮겨 적어야 했다. 이 문서가 그 뒤늦은 이관이다.
2. **매핑을 일회용 스크립트의 문자열 split으로 때웠다.** 보정 스크립트에서 `stn_Name.split()[0]`로 시군구를 뽑았고, 이걸 별도 산출물로 승격하지 않았다.
3. **국소적 실패 신호를 무시했다.** 그 split에서 **7개 지점이 매칭 실패**하는 걸 보고 "검증에는 충분하다"고 넘겼다. 그 7개가 광역시 행정계층 불일치라는 구조적 신호였고, 전 지점으로 확대하면 143개 구역이 비는 문제였다. 국소적으로 무해한 실패가 전역적으로는 설계 결함의 증상일 수 있다.

추가로, 모델 docstring에 "역할: … region 매핑"이라 적혀 있는데 `region_id` 컬럼이 없는 상태를 보고도 지나쳤다 — CLAUDE.md §3.3이 경고하는 명세·코드 괴리다.

## 2. 2계층 설계 — 관측망이 두 개인 것은 의도된 것이다

이 부분은 제가 처음 오해했던 것으로, 정정한다.

| 계층 | 관측망 | 지점 수 | 코드 형식 | 역할 |
|---|---|---|---|---|
| **1차** | 농업기상 (농진청) | **216개** | `230802A001` | 주 데이터원. **일사량 `srqty`·일조 `sun_Time`이 여기에만 있다** |
| **2차** | 기상청 AWS | 약 510개 | `108` | **1차의 결측 보완** + 농업기상 지점이 없는 구역 커버 |

지점 수는 실제 응답에서 셌다(2024년 1·4·7·10월 고유 `stn_Cd` = 216). 문서 곳곳의 "510개"는 AWS 기준이므로, **숫자를 계층별로 분리해 표기**해야 혼동이 재발하지 않는다.

**두 코드 체계는 조인되지 않는다.** 그래서 계층을 잇는 것은 지점코드가 아니라 **구역(region)** 이어야 한다 — 즉 두 관측망 모두 `region_id`로 배정돼야 비로소 "농업기상이 비면 AWS로 채운다"가 성립한다. 이것이 매핑이 필요한 진짜 이유다.

### 2.1 그래서 `kma_observation_point`의 설계는 옳았다

`point_code, name, lat, lon, altitude` — **`lat`/`lon`이 있는 것이 핵심**이다. AWS 지점은 좌표가 있으므로 이름 매칭의 행정계층 문제를 겪지 않고 `latlon_to_grid()`로 바로 구역에 배정된다. 원 설계자의 의도가 맞았다.

빠진 것은 `region_id`(배정 결과를 담을 자리)와 `network`(어느 관측망인지) 두 컬럼이다.

## 3. 사실관계 정정 — 무엇이 실제로 지워졌나

### 3.1 매핑 컬럼은 원래 없었다

```
grep -c "region_id" backend/app/models/kma_observation_point.py           → 0
grep -c "region_id" backend/alembic/versions/0015_kma_observation_point.py → 0
```

head 원본 `0015`도 컬럼이 5개(`point_code, name, lat, lon, altitude`)뿐이었다. 매핑은 docstring의 의도로만 있었고 스키마에는 없었다. 내가 지운 것은 **지점 목록 샘플 15행**이며 테이블과 모델은 살아 있다.

책임을 줄이려는 말이 아니다 — **지운 것보다 없던 것이 더 큰 문제**라는 뜻이다.

### 3.2 지운 15행은 AWS 코드였다 (계층상 맞는 데이터였다)

| | 코드 | 예시 |
|---|---|---|
| 구 `0015` 샘플 15행 | 3자리 | `108`(서울), `131`(인천), `135`(동두천) |
| 1차 데이터 실제 코드 | 10자리 | `011104F031`, `230802A001` |

§2의 2계층 설계를 알고 다시 보면, 그 15행은 **AWS 계층의 시작이었으므로 데이터 자체는 맞았다.** 다만 510개 중 15개만 든 부분 샘플이었고, 마이그레이션에 부분 마스터 데이터를 넣는 것은 CLAUDE.md §10 위반이라 **시드를 스크립트로 빼는 판단은 유지한다.** 잘못은 §1-1(요구사항 이관 실패)이다.

### 3.3 `0014` 삭제는 이 문제와 무관하다

매핑이 두 종류다. 혼동을 막기 위해 분명히 해 둔다.

| 매핑 | 잇는 대상 | 상태 |
|---|---|---|
| `region_grid` | 구역 256 → 기상청 **단기예보 격자**(nx, ny) | ✅ **256/256** (`docs/seed/region_grid_seed.csv` + `scripts/load_region_grid.py`) |
| `kma_observation_point` | **관측지점 → 구역** | ❌ 없음 — 이 보고서 주제 |

삭제한 `0014`는 위쪽이고 CSV가 256개 전부를 더 정확히 적재한다. 다만 아래쪽 해결에 **위쪽을 재사용한다**(§6).

## 4. 이름 매칭 재평가 — "못 쓴다"는 너무 단정적이었다

첫 판정에서 `stn_Name`의 첫 토큰만 대조해 **113/256**을 얻고 "메커니즘을 바꿔야 한다"고 결론했다. 지점명 구조를 다시 보니 2번째 토큰이 단서였다.

```
대구시 북구      → '북구'가 region_seed에 있다
부산시 강서구    → '강서구'
수원시 서둔동    → '서둔동' (bjd_to_region.csv의 읍면동)
천안시 성환읍    → '성환읍'
강릉 안반덕이    → '강릉' + 시 접미사
청원군 오창읍    → '오창읍' (청원군은 2014년 청주 통합으로 폐지)
```

### 4.1 다단계 해석기 실측 결과

| 단계 | 방법 | 해결 지점 수 |
|---|---|---|
| 1 | 1번째 토큰 = 시군구명 직접 | 180 |
| 2 | 2번째 토큰 = 구 이름 | 4 |
| 3 | 2번째 토큰 = 읍면동 (`bjd_to_region.csv` 5,066행) | 21 |
| 4 | 1번째 토큰 + `시`/`군` 접미사 보정 | 7 |
| — | 미해결 | **4** |

```
배정된 구역: 128 / 256   (1단계만 쓸 때 113)
미해결 지점: 고양시 덕양구, 안산시 상록구, 용인시 처인구, 포항시 북구, 동방로거테스트
```

미해결 4개는 내 시도(sido) 모호성 판정 로직이 엉성해서 생긴 것이고(구 이름은 `region_seed`에 실제로 있다), 다듬으면 **216개 중 215개**가 붙는다. `동방로거테스트`는 테스트 지점이라 제외 대상이다.

→ **이름 매칭은 1차 계층에 실용적으로 쓸 수 있다.** 첫 판정을 정정한다. 다만 마스터 데이터에 의존하는 문자열 규칙이라 행정구역 개편 때 깨질 수 있으므로, 배정 결과를 시드 CSV로 고정하고 스크립트로만 재생성하는 형태여야 한다.

### 4.2 남는 128개 구역은 이름 문제가 아니라 **지점이 없다**

미커버 구역의 시도 분포:

| 시도 | 미커버 / 전체 |
|---|---|
| 서울특별시 | 25 / 25 |
| 부산광역시 | 16 / 16 |
| 경기도 | 34 / 47 |
| 인천광역시 | 10 / 11 |
| 대구광역시 | 8 / 9 |

농업기상은 농경지 관측망이라 **도심 구에 지점이 없는 것이 자연스럽다.** 이름 규칙을 더 손봐도 채워지지 않는다. 여기가 정확히 **AWS 보완 계층 + 최근접 대체**가 필요한 지점이다.

### 4.3 다중 지점 구역(36개)은 집계 규칙이 필요하다

```
구역당 지점 수: 1개→76구역, 2개→24, 3개→7, 4개→2, 5개→1, 7개→1, 15개→1
```

한 구역에 15개까지 있다. 어느 값을 쓸지 정하지 않으면 같은 구역이 호출마다 다른 값을 낼 수 있다 — 결정론 위반(§2). **[확인 필요]** — 임의로 정하지 않는다.

1. **구역 중심 격자에 최근접 지점 1개** (단순·결정론적, 추천)
2. 전 지점 평균 (표본은 늘지만 산지 지점이 섞이면 왜곡 — 예: `태백시 매봉산`)
3. 구역 대표고도에 가장 가까운 지점 (데이터 요구 증가)

## 5. 이 문제가 검증된 일조 정확도를 훼손했는가 — 아니다

정확도 검증(R²=0.903)에 이 fragile 매핑으로 얻은 위도를 썼으므로 확인했다.

**위도 오차 민감도** (같은 일사량, 위도만 이동):

| 위도 오차 | 1월 | 4월 | 7월 | 10월 |
|---|---|---|---|---|
| ±0.023° (격자 중심 오차) | 0.3분 | 0.1분 | 0.1분 | 0.3분 |
| ±0.1° | 1.3분 | 0.5분 | 0.2분 | 1.1분 |
| ±0.2° | 2.7분 | 1.0분 | 0.5분 | 2.3분 |
| ±0.5° (약 55km, 과장된 최악) | 6.8분 | 2.4분 | 1.2분 | 5.7분 |

검증된 MAE는 **0.583h = 35분**이다. 위도가 0.5° 틀려도 기여는 7분 이하로 MAE의 20% 미만이다. 물리적으로도 당연하다 — 위도는 가조시간 `N`과 지구외일사량 `Ra`를 통해서만 들어오고 둘 다 완만하게 변한다. 지배항은 실측 `Rs/Ra`다.

**따라서 정확도 수치는 유효하다.** 매핑 문제는 정확도가 아니라 **커버리지** 문제다.

정직하게 덧붙이면 — 보정 표본에서 **749행이 "지점 위도 없음"으로 버려졌고 대부분이 광역시·통합시 지점**이다. 즉 도시권이 보정에서 체계적으로 빠졌다. 채택 경로가 일사량 기반이라 도시 열섬 영향은 작지만, §4.1의 해석기로 매핑을 고친 뒤 **재보정해 계수가 흔들리지 않는지 확인**하는 것이 옳다.

## 6. 제안 설계 — 계층별로 다른 메커니즘

두 계층의 사정이 다르므로 방법도 다르다. 새로 만들 것은 거의 없다.

### 6.1 2차(AWS) — 좌표 기반. **지금 바로 가능하다**

```
getAwsStnLstTbl (stn_id, lat, lon, ht)
   └─ latlon_to_grid() ──▶ 격자(nx,ny) ──▶ region_grid 조회 ──▶ region_id
        (구현·테스트 완료)                    (256/256 완비)
```

`기상청_API-Guide.md`가 이미 `getAwsStnLstTbl`로 `stn_id`/`lat`/`lon`/`ht`를 준다고 명시한다. **명세서가 있으므로 막힌 것이 없다.** 좌표로 잇기 때문에 "부산시냐 해운대구냐" 같은 계층 문제가 발생하지 않는다 — 이것이 이 경로의 장점이다.

### 6.2 1차(농업기상) — 이름 기반. 좌표가 없다

농업기상 관측 응답에 위경도가 없다(`stn_Cd`, `stn_Name`만).

| 좌표 확보 후보 | 상태 |
|---|---|
| 농업기상 관측지점 정보 API | `.env`에 `weather_observatory_api` 키가 **이미 있으나 기술명세서가 없다.** 엔드포인트 3개를 시도해 전부 `404 API not found` → 추측을 멈췄다(§3.4). **명세서 확보 시 좌표 기반으로 전환 권장** |
| VWorld 지오코딩 | `vworld_api` 키가 비어 있고, 약관상 결과를 DB에 저장할 수 없다(`gen_region_grid_seed.py` docstring). **부적합** |

→ 당장은 **§4.1 다단계 이름 해석기**로 간다(215/216 지점). 좌표 API 명세서가 확보되면 좌표 기반으로 바꾼다.

### 6.3 미커버 구역 — 이미 있는 대체 로직 재사용

`climatology_service.load_climatology()`가 **평년치 없는 지역을 격자 거리 최근접 지역으로 대체하고 그 사실을 표기**하는 로직을 이미 갖고 있다(102/256 커버 문제를 이렇게 처리했다). 관측지점도 같은 패턴으로:

1. 구역에 농업기상 지점이 있으면 그것
2. 없으면 **AWS 지점**(2차 계층)
3. 둘 다 없으면 **격자 최근접 지점** + `substituted_from`·`distance_km` 표기(§1-4)

새 알고리즘이 아니라 검증된 패턴의 재사용이다.

### 6.4 스키마

```sql
ALTER TABLE kma_observation_point
    ADD COLUMN region_id INTEGER REFERENCES region(id),
    ADD COLUMN network   VARCHAR(16) NOT NULL;  -- 'agri' | 'kma_aws'
```

`network`가 필요한 이유: 216개 농업기상과 510개 AWS가 구분 없이 한 테이블에 섞이면 §2의 계층 구분이 스키마에서 사라진다. 코드 체계가 다르므로 구분자가 있어야 결측 보완 로직이 "1차인지 2차인지"를 판단할 수 있다.

테이블명이 `kma_`로 시작해 AWS 전용처럼 읽히는데 농업기상도 담을 것이므로 `weather_observation_point`로 개명하는 것도 검토할 만하다.

| 농업기상 | Base URL에 스킴 없음 | `https://` 추가 |

### 보강한 내용 (원문에 없어 실측으로 확정)

**농업기상** — 원문이 필드명만 나열하고 **단위를 적지 않는다.** 단위 표를 추가했다. 특히:

- **`sun_Time`은 분(minute)** — 시간으로 오해하면 60배 틀어진다. 실측 분포 최대 793이 시간이면 불가능하고 분이면 13.2h로 국내 최대 가조시간과 맞는다. `condens_Time`도 분.
- `date`는 응답이 `YYYY-MM-DD`(하이픈)인데 요청 파라미터는 `YYYYMMDD`로 형식이 다르다.
- 결측이 빈 문자열(`<sun_Time></sun_Time>`)로 오므로 `0`으로 파싱하면 안 된다. `rn` 결측은 `-999`.
- `sun_Time`은 26,071행 중 8,745행만 보유 — `srqty`가 더 잘 채워진다.
- **센서 불량 지점 존재**: 65개 중 5개가 일사–일조 상관 R²<0.2, `Rs/Ra>0.80`(물리 불가) 365행.
- 지점 216개이며 `동방로거테스트` 테스트 지점이 섞여 있다.
- `Page_Size=9999`로 전국 한 달 1콜 가능. 쿼터가 있다(`429 API token quota exceeded` 실측).

**농경지화학성** — 주1~주5를 추가했다: 구간 오타, 개방구간 대표값(이론 상한 사용 시 유효인산 2008 mg/kg 폭주), 헤더 케이스가 `result_Code`(소문자)라 틀리면 성공이 에러로 둔갑, 조사연도 필드 없음, 경지구분(논/밭/시설/과수)별 구간 경계가 서로 달라 한 표를 돌려쓰면 안 됨.

## 9. 최종 해결 (2026-07-26 완료)

### 9.1 전환점 — `Sample-code.py`

§6.2에서 "농업기상 지점 좌표를 못 구해서 이름 매칭으로 간다"고 결론했는데, 제공받은
`Sample-code.py`에 엔드포인트가 있었다.

```python
url = 'http://apis.data.go.kr/1390802/AgriWeather/getObsrSpotList'
```

제가 추측했던 `.../AgriWeather/WeatherObsrInfo/V3/GnrlWeather/getWeatherObsrSpotList` 등은
전부 404였다. 실제 경로는 `WeatherObsrInfo/V3/` **하위가 아니라 `AgriWeather/` 최상위**였다.
추측으로는 닿을 수 없는 구조였고, 그래서 §3.4대로 추측을 멈춘 판단은 맞았지만 —
**이미 리포에 있는 자료를 먼저 찾아보지 않은 것이 제 실수다.**

실호출로 확인한 응답(`total_Count=218`):

```xml
<Obsr_Spot_Code>336812A001</Obsr_Spot_Code>
<Obsr_Spot_Nm>아산시 염치읍</Obsr_Spot_Nm>
<Instl_La>36.8257331962636</Instl_La>   ← 위도
<Instl_Lo>126.9679648119612</Instl_Lo>  ← 경도
<Instl_Al>10.0</Instl_Al>
<Instl_Adres>충남 아산시 염치읍 염치1길 40</Instl_Adres>
```

### 9.2 그래서 이름 매칭을 통째로 버렸다

§4에서 공들여 만든 4단계 이름 해석기(시군구 직접 → 통합시 구 → 읍면동 → 접미사 보정)는
**삭제했다.** 좌표가 있으면 필요 없다.

| | 이름 기반(폐기) | 좌표 기반(채택) |
|---|---|---|
| 농업기상 배정 | 215/216 (4단계 규칙) | **217/218** |
| 광역시·통합시 | 특수 처리 필요 | 문제 자체가 없음 |
| 행정구역 개편 | **깨진다** | 영향 없음 |
| 최대 대체 거리 | 15.8km | **11.2km** |

행정계층 불일치("부산시"냐 "해운대구"냐), 접미사 누락("강릉" vs "강릉시"), 폐지된 구역
("청원군") — §4.2에서 진단한 세 가지 실패 패턴이 **한꺼번에 사라졌다.** 좌표는 행정
명칭 체계를 따지지 않는다.

### 9.3 배정 메커니즘 — 양쪽 동일

```
지점 위경도 ──latlon_to_grid()──▶ 격자(nx,ny) ──격자 거리 최근접──▶ region_id + distance_km
```

**격자 정확 일치를 쓰지 않는 이유**(§6.1 설계의 구멍이었다): `region_grid`는 구역당 대표
격자 1개(고유 224개)만 갖는데 전국은 149×253=37,697칸이다. 정확 일치를 요구하면 534개
AWS 지점 중 **71개만** 붙었다. 최근접으로 바꾸고 **거리를 함께 기록**한다 — 거리를 숨기면
40km 떨어진 관측값을 그 구역 실측처럼 보이게 만든다(§18-4).

### 9.4 최종 결과

```
기상청 AWS      534개 → 배정 516,  40km 초과 18 (독도·격렬비도 등 원거리 도서)
농업기상        218개 → 배정 217,  40km 초과  1
────────────────────────────────────────────────
구역 안에 지점이 있는 구역: 농업기상 134 / AWS 191 / 합집합 198
최근접 대체 허용 시:        224/224 격자 전부 배정 (최대 거리 11.2km)
```

**256개 구역 전부가 관측지점을 갖는다.** 구역 '안'에 지점이 있는 경우만 세면 198이지만,
확정된 최근접 규칙을 적용하면 격자 매핑이 있는 224개 격자(=256구역) 전체가 커버된다.

### 9.6 확정된 결정 규칙 (사람 승인)

1. **다중 지점 → 최근접 1개.** 한 구역에 지점이 15개까지 있어 평균은 산지·평지를 섞고
   "어느 값을 썼는지"가 불명확해진다. 최근접은 결정론적이고 설명 가능하다.
2. **1차(농업기상) 우선.** 일사량·일조시간이 여기에만 있어 장기 탭 일조 지표가 의존한다.
   없으면 2차(AWS)로 내려간다.
3. **거리를 항상 함께 반환**하고 UI에 표기한다(`StationMatch.limitation_note()`).
   AWS로 내려간 경우 "일조 자료는 제공되지 않습니다"도 함께 알린다.
4. 동거리는 `point_code` 순으로 고정해 결정론을 보장한다(§2).
5. **40km 초과는 결측 처리.** 아무 값이나 주는 것보다 데이터 없음이 정직하다(§18-4).

### 9.7 부수적으로 고친 것

- **`VWORLD_APIkey`가 로드되지 않고 있었다.** `.env` 키가 `VWORLD_APIkey`인데 config
  필드는 `vworld_api`였다 — 대소문자는 무시되지만 `key` 접미사가 달라 매칭 실패였다.
  §3-①의 헤더 대소문자 버그와 같은 계열(조용히 빈 값이 되는 불일치)이다. 이제 8개 키 전부 로드된다.
- `weather_apihub_key` 필드 추가. apihub는 data.go.kr과 **별개 인증 체계**여서
  data.go.kr 키를 넣으면 401이다.
- 문서의 "AWS 510개"는 실제 **534개**(2025-01 발표 기준)였다. 농업기상도 216→**218개**.

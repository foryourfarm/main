# 밭 주소를 법정동 말단(리)까지 받는다 — 백엔드 설계

> 작성: 2026-07-31. 상태: **설계 확정, 구현 미착수.**
> 결정 근거는 `nexttodo.md` §"리 단위 전환"에 실측과 함께 있다.

## 1. 원칙 하나

**선택 단위 = 법정동 말단(leaf) = 흙토람 조회 단위.**

지금은 셋이 어긋나 있다. 유저는 읍·면을 고르는데 흙토람은 읍·면 코드에 데이터가 없어
(리 자리 `00` → 301 "데이터 없음") 백엔드가 리 5곳을 몰래 평균한다. 이 설계는 셋을 일치시킨다.

- 리가 있는 읍·면(1,411개) → 리를 고른다
- 리가 없는 동·읍·면(3,655개) → 그 자체가 말단이라 지금 그대로 고른다

"리가 있으면 내려가고, 없으면 윗선에서 자른다"는 곧 법정동코드 트리의 말단을 고르는 것이다.
별도 분기 규칙이 아니라 한 규칙이다 — 조건부 UI가 필요 없는 이유다.

## 2. 데이터 (`docs/seed/bjd_to_region.csv`, 실측)

| 구분 | 행 수 |
|---|---|
| 전체 법정동 | 20,275 |
| ├ 읍면동 | 5,066 |
| └ 리 | 15,209 |
| **선택 가능(말단)** | **18,864** = 동·읍·면 3,655 + 리 15,209 |
| 중간 노드(리를 가진 읍·면) | 1,411 |

정합성 확인: 리 코드 전부 10자리, 부모 읍면동 행이 없는 고아 리 0건, `bjd_code` 중복 0건,
`eupmyeondong` 빈 리 0건. 리 코드는 부모 면 코드와 앞 8자리를 공유한다(공음면 `5279034000`
→ 구암리 `5279034023`) — 기존 `ri_codes()`의 `bjd_code[:8]` 그룹핑이 그대로 맞다.

## 3. 스키마 변경 없음

| 컬럼 | 지금 | 리 코드 수용 |
|---|---|---|
| `district.bjd_code` | PK, 길이 제한 없는 `str` | 그대로 |
| `user_farm.bjd_code` | FK → `district.bjd_code` | 그대로 |
| `district_soil.bjd_code` | FK → `district.bjd_code` | 그대로 |

**마이그레이션 없음. 대신 FK가 배포 순서를 강제한다** — `district`에 리 행이 들어간 뒤에야
리 코드로 밭 등록/토양 캐시가 가능하다. 순서가 뒤집히면 FK 위반으로 등록이 깨진다.

배포 순서: ① `load_districts.py` 실행 → ② 백엔드 배포 → ③ 프론트 배포.

`parent_bjd_code` 컬럼은 두지 않는다. 계층은 `name`에 담고(§4.1), 말단 판정은 이미 있는
`ri_codes()`로 한다. 컬럼을 추가하면 마이그레이션이 생기고, 얻는 건 없다.

## 4. 변경 지점 (4개 파일)

### 4.1 `scripts/load_districts.py` — 리 적재

- `if r["ri"]: continue`(39행) 제거
- `name` 조립: 리 행은 `f"{eupmyeondong} {ri}"` → `"공음면 구암리"`. 읍면동 행은 지금대로 `"공음면"`
- 파일 상단 주석 6~7행("리 레벨은 넣지 않는다 — 조회 단위가 읍면동")은 **근거가 뒤집혔으니 함께 고친다.**
  흙토람 조회 단위는 읍면동이 아니라 말단이다
- `bjd_code` PK upsert라 멱등 — 재실행 안전. 5,066 → 20,275행

`name`에 면 이름을 넣는 이유: `District.name` 정렬만으로 같은 면의 리가 붙어서 나온다.
계층 컬럼 없이 화면에서 "어느 면의 리인지" 읽힌다.

### 4.2 `farm_service.list_districts` — 중간 노드 제외

리를 가진 읍·면(1,411개)을 목록에서 뺀다. 판정은 `ri_codes(bjd_code)`가 비었는지 — 새 쿼리·새
컬럼 없이 기존 헬퍼 재사용(`lru_cache`라 비용 0).

**행은 DB에 남긴다.** farm 10·11·12가 면 코드로 FK 걸려 있고, 그 밭들은 §4.3의 리-풀 폴백을
계속 쓴다. "목록에서 안 보임 ≠ 삭제"다.

호출 결과 크기가 커진다(시군당 중앙값 13 → 69, 최대 87 → 236(상주시)). §4.4의 근거.

**구현 시 발견 — `ri_codes()`를 말단 판정에 그대로 쓰면 안 된다.** 리와 부모 면이 앞 8자리를
공유하므로 `ri_codes("5279034023")`(구암리)는 공음면 리 전체를 돌려준다 → "리를 가졌으니 면"으로
오판한다. 그래서 `is_leaf_bjd()`를 별도로 뒀다: 법정동코드 뒤 2자리가 `00`이 아니면 리(=말단),
`00`이면 리 존재 여부로 판정. 뒤 2자리 규칙은 시드 20,275행 전수 확인했다(예외 0건).

말단 제한은 **선택지를 좁히는 쪽에만** 둔다. `_validate_location_and_crop`에 넣으면 면 코드로
등록된 기존 밭이 라벨만 고쳐도 검증을 다시 타서 자기 주소를 못 고치게 된다.

### 4.3 `district_soil_service` — 리-풀 폴백을 **삭제**한다 ★방향 전환★

당초 이 절은 "폴백은 유지하고 출처 문구만 정직하게"였다. **그 판단을 뒤집었다.**

폴백이 존재한 이유는 "면만 알고 리를 모른다"였다. §4.2로 유저가 리를 직접 고르게 된 순간
전제가 사라진다. 실측으로 확인했다 — **리 코드 데이터 적중률 40/40**(14개 시도 균등 표집 28곳
+ 고창 공음면 12곳, 통합전 코드 재시도 포함). 리가 없는 동은 `ri_codes()`가 빈 리스트라 폴백
루프를 아예 돌지 않는다. 즉 폴백이 탈 자리는 **리 전환 전에 면 코드로 등록된 밭**뿐이다.

문구만 고치면 부족한 이유: §18-4는 만족하지만 유저가 보는 **점수는 여전히 남의 땅 점수**다.
이웃 리 4~5곳 평균은 실측 EC 0.47~8.15(17배), 점수 오차 평균 34.7점·최대 60점·등급 변경 4/6이다.
CLAUDE.md §1 가치 1(정확성 우선)과 PRD 철학 1에 그대로 걸린다. 게다가 `is_estimated=False`로
저장돼 "추정 아님"으로 기록된다. 숫자가 채워져 있으면 유저가 리를 다시 고를 이유도 못 느낀다.

지운 것: `RI_SAMPLE_LIMIT`, `_fetch_exams`의 폴백 블록, `queried_code.startswith("… 리 ")` 스니핑.
`ri_codes()`는 `is_leaf_bjd()`가 쓰므로 남는다. `_fetch_exams`의 두 번째 반환값이 **항상 실제
법정동코드 또는 None**이 되어 문자열 유니온이 사라진다.

대신 출처 문구를 순수 함수 `source_label(bjd_code, queried_code, field_type)`로 뽑아 테스트로
고정했다. 화면 footer까지 그대로 나가는 문구라 유저와의 약속이다(§18-4):

| 경우 | 문구 |
|---|---|
| 말단 조회 성공 | `흙토람 토양검정(법정동 5279034023, 경지구분 3), 표본 N건` |
| 통합전 코드로 성공 | `흙토람 토양검정(법정동 4677038021 통합전코드, 경지구분 2), 표본 N건` |
| 리를 가진 읍·면 | `흙토람 토양검정(읍·면 단위로는 기록 없음 — 리를 선택하면 조회됩니다), 표본 0건` |
| 말단인데 표본 없음 | `흙토람 토양검정(조회 실패 — 표본 없음), 표본 0건` |

마지막 두 줄을 가른 이유: 도시 동은 리가 없으니 "리를 선택하라"고 하면 거짓 안내가 된다.

결측은 이미 정직하게 처리된다 — 채점 커버리지 한계 문구(PR #57 #3)가 미채점 지표를 밝히고,
FE는 "읍/면/동을 다시 선택하면 토양 데이터가 정확해집니다"를 이미 노출한다.

### 4.4 FE `FarmForm.tsx` — `<select>` → datalist 입력

시군당 선택지가 중앙값 69·최대 236개(제주시)가 되어 `<select>` 스크롤로는 못 찾는다.
시/군에 이미 넣은 datalist 검색(#5)과 같은 패턴으로 바꾼다. 라벨은 "읍/면/동" → "읍/면/동·리",
힌트 문구도 "리 단위로 가져옵니다"로.

수정 모드에서 목록 도착 전 현재 값을 보여주는 처리(140~142행)는 datalist에서도 필요하다.

## 5. 기존 밭 (마이그레이션하지 않는다)

면 코드로 등록된 밭(farm 10·11·12)은 **토양이 NULL로 남는다.** 유저 동의 없이 밭 주소를 임의의
리로 바꾸는 건 데이터 위조이고, 이웃 리 평균을 채워 넣는 것도 같은 문제다(§4.3). 유저가 설정
화면에서 리까지 다시 고르면 그때 정확한 값이 들어온다 — `update_farm`이 `bjd_code` 변경 시
`soil_state`를 재생성하므로 별도 처리가 없다.

`district_soil` 캐시는 표본 0건이면 자동 재조회되므로(`d3e51c1`) 수동 정리도 필요 없다.

**`scripts/repair_empty_soil_state.py`는 이제 아무것도 복구하지 못한다** — 면 코드 밭은 항상
0건이고, farm 7(도시 동)은 흙토람에 실제로 표본이 없다. 리 코드로 등록된 밭은 등록 시점에
바로 값이 들어오므로 복구 대상이 아니다. 삭제 후보로 남긴다(§9).

## 9. 남은 정리 (별건)

- `scripts/repair_empty_soil_state.py` 삭제 — 위 이유로 동작할 대상이 없다. 지우기 전 확인 필요.
- `nexttodo.md`의 "기존 밭 토양 복구" 항목 → "유저가 리를 다시 고른다"로 대체.

## 6. 얻는 것과 못 얻는 것

**얻는 것**
- 정확도: 부여 장암면 실측 면 평균 vs 리 실측 평균 |차이| 34.7점, 최대 60점, 6개 리 중 4개가 등급 변경
- 호출량: 등록당 리 5회(13.6초) → 1회(약 3초)
- 정직성: 출처가 "리 5곳 평균"이 아니라 유저가 고른 그 리가 된다

**못 얻는 것 — EC**
공음면 시설 실측에서 용수리 한 곳의 EC 범위(0.47~21.05)가 면 전체 범위(0.14~21.05)를 그대로
담는다. 시설 EC는 개별 하우스 시비 이력이 지배해서 행정구역으로 수렴하지 않는다. 리로 내려가도
EC는 "지역 대표값"이 아니다 — pH(리 평균 5.05~7.80)·유기물은 이득이 분명하다.
EC 전용 한계 문구는 이 설계 범위 밖의 별건으로 남긴다.

## 7. 테스트 (§3-6, 최소 2개)

1. **말단 필터** — 리를 가진 면 코드는 목록에 없고, 그 면의 리는 있고, 리 없는 동은 그대로 있다.
   `ri_codes()` 기반 순수 판정이라 네트워크·DB 불필요.
2. **리 코드 폴백** — 표본 0건인 리 코드로 들어올 때 후보에서 자기 자신이 빠지고, 출처 문구가
   면 이름으로 적히는지(리 코드를 면처럼 적지 않는지).

기존 `test_district_soil.py`의 `TestRiCodes` 3개는 면·동 입력 기준이라 그대로 통과한다.
`test_is_sorted_for_determinism`은 유지 — 상한으로 앞을 자르는 폴백이 남으므로 순서가 여전히
결과를 바꾼다.

## 8. FE 인계 (§3-7)

구현 시 `docs/farm-settings-api.md`를 갱신한다 —
`GET /api/v1/regions/{region_id}/districts`의 응답 계약(`bjd_code`/`name`)은 바뀌지 않지만
**의미가 바뀐다**: 반환 항목이 읍면동이 아니라 법정동 말단이고, `name`이 `"공음면 구암리"`처럼
계층을 포함하며, 건수가 시군당 최대 236개다.

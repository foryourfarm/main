# LLM 연동 가이드 (백엔드용)

> "어떻게 붙일지"의 계약·순서를 정하는 문서. 관련 규칙: [CLAUDE.md](../CLAUDE.md) §13, 제품 스코프: [PRD.md](../PRD.md) §10.
> 백엔드는 **Python(FastAPI)**. 게임 기획은 폐기됨.

## 0. 한 줄 요약

로컬 LLM은 **정형 분석 결과를 초보 귀농인 눈높이 한국어로 옮기는 렌더러**다.
계산·판단은 전부 백엔드 룰 엔진이 하고, LLM은 자연어 변환만 한다.
**핵심 기능(추천/커리큘럼/설명)은 직접 주입(RAG 아님).** RAG는 상담 챗봇에만 — 큐레이션 문서 코퍼스를 `pgvector`로 검색해 근거 주입.

## 1. 아키텍처 위치

```
services (유스케이스)
  → 룰 엔진: 적합도(장기)·위험신호·토양변화 → 점수/등급/플래그  [결정론, LLM 아님]
  → 프롬프트 조립: 위 결과 + DB 정형 데이터 → 프롬프트
  → LlmClient.generate(prompt) → 한국어 텍스트
       └ 실패 시 → 규칙 기반 폴백 문구
```

- **핵심 기능은 RAG 없음.** `(지역, 작물, 밭)`이 정해지면 필요한 DB 행이 곧바로 특정되므로 검색이 아니라 직접 주입.
- **챗봇만 RAG**: 큐레이션 농업 문서를 bge-m3로 임베딩→`pgvector`(`knowledge_chunk`, DB.md §3.15)에 저장, 질문 유사 조각을 검색해 근거 주입. 별도 벡터DB 아님. 문서 못 찾으면 "확실치 않음/전문가 상담" 폴백(환각 방지).
- LLM 역할(PRD §10): ①단기 행동추천(필수·메인) ②장기 커리큘럼 서술 ③토양/지역 특성 설명 ④상담 챗봇(RAG). 자유 대화로 확장 안 함.

## 2. 생성 타이밍 — 사전생성 vs 실시간 (중요)

| 종류 | 방식 | 이유 |
|---|---|---|
| 일일 행동추천·장기 커리큘럼 | **스케줄러 사전생성** → `daily_recommendation`에 저장, 요청은 캐시만 읽음 | 로컬 LLM은 느림(수 초). GPU 1장은 요청을 직렬 처리하므로 아침 동시접속에 취약 → 미리 생성해 회피 |
| 상담 챗봇 | **요청 시 실시간** + 스트리밍 | 대화라 사전생성 불가. 동시성은 **vLLM**(continuous batching)로 처리 |

- 개발은 **Ollama**(설치 쉬움, 모델 교체 편함), 다중 사용자 서빙은 **vLLM**(OpenAI 호환). 둘 다 OpenAI 호환 API라 `LlmClient` 뒤에서 교체 가능.

## 3. 구현 순서 (거꾸로 하지 말 것)

1. **룰 엔진**(적합도/위험신호) 구현 → 그 **출력 스키마(pydantic) 확정**. ([DB.md](../DB.md) §8)
2. 그 스키마를 입력으로 받는 **프롬프트 조립** 작성.
3. **LlmClient** 호출 + **폴백** 연결.

> 프롬프트 조립을 룰 엔진 출력 스키마보다 먼저 짜면 다시 쓰게 된다.

## 4. LlmClient 인터페이스 (계약)

모델/런타임 교체가 가능하도록 추상화(CLAUDE.md §13). Python 예:

```python
from typing import Protocol

class LlmClient(Protocol):
    def generate(self, prompt: str) -> str:
        """프롬프트 → 한국어 텍스트. 실패 시 예외(폴백은 호출부 책임)."""
        ...
```

- 구현체: `OllamaClient` / `VllmClient`(둘 다 OpenAI 호환 `/v1/chat/completions` 또는 Ollama `/api/generate`). `httpx`로 호출.
- 타임아웃·재시도는 구현체에서. LLM이 서비스를 막으면 안 되므로 타임아웃 짧게(수 초) + 초과 시 폴백.

## 5. 폴백 규칙 (필수)

호출 실패(타임아웃/연결불가/빈 응답/이상 출력) 시 **규칙 기반 기본 문구**로 떨어진다. 서비스는 멈추지 않는다(CLAUDE.md §13, §18-5). `daily_recommendation.is_llm=false`로 기록.

```python
try:
    text = llm.generate(prompt)
    assert text.strip()            # 최소 검증: 비어있지 않음
except Exception:
    text = rule_based_fallback(score, grade, risk_flags)  # 예: "적합도 82점(A). 오늘 야간 저온 주의."
```

- 폴백 문구는 정형 데이터만으로 조립 가능해야 함(LLM 없이도 최소 정보 전달).

## 6. Ollama 호출 실물 (검증용 curl)

서버 세팅은 [infra/ollama-vm/README.md](../infra/ollama-vm/README.md) 참고.

```bash
curl -s http://<LLM_HOST>:11434/api/generate -d '{
  "model": "exaone3.5:7.8b",
  "prompt": "너는 귀농 상담 전문가다. 아래 분석을 초보 농부에게 친근하게 설명해라.\n적합도 82점(A등급). 토양 pH 6.2(적정), EC 1.1(적정). 오늘 야간 최저기온 3도로 저온 주의.",
  "stream": false,
  "options": { "temperature": 0.4 }
}'
```

- 응답 JSON의 `response`가 생성 텍스트. `temperature`는 낮게(0.3~0.5, 사실 기반이라 일관성 우선).
- 챗봇 스트리밍은 `stream:true` + SSE(vLLM은 OpenAI 호환 스트리밍).

## 7. 설정값

`app/core/config.py`(pydantic-settings)가 환경변수로 주입:

```
LLM_BASE_URL=http://localhost:11434     # GCP는 VM 내부 IP (infra/ollama-vm)

```

- 비밀 아님이지만 서버 환경변수로만. URL에 인증정보 넣지 말 것.

## 8. 단기 행동추천 (PRD §10-1, 구현 완료)

`app/prompts/daily_advice.py` (`advice-v1`) + `app/services/advice_service.py`.

**구조는 "규칙 문구가 먼저, LLM은 다듬기"다.** LLM에게 위험 목록을 주고 알아서 쓰게 하지
않는다 — 프롬프트에 완성된 [기본 문구]를 통째로 넣고 표현만 바꾸게 한다.

```
summarize_risks()  위험신호 → 값·허용구간 정형 요약  (순수, 기상만)
rule_advice()      정형 요약 → 규칙 문구             (순수, 품질 하한선)
polish()           규칙 문구 → 다듬은 문구            (실패 시 None → 규칙 문구 사용)
```

**FE 계약** — `GET /api/v1/farms/{id}/advice` (단기 탭과 **별도 요청**):

```json
{ "text": "8월 2일 낮 기온이 27.2℃로 …", "is_llm": true,
  "soil_text": "이 밭이 속한 설악면 선촌리의 토양검정 표본 기준으로는 …" }
```

| 필드 | 뜻 |
|---|---|
| `text` | 기상 기반 오늘의 행동. 매일 바뀌므로 LLM이 다듬는다 |
| `is_llm` | false면 규칙 문구 — 화면에 구분 표기(§18-4). **`soil_text`에는 해당 없음** |
| `soil_text` | 이 밭이 속한 법정동의 토양 특성. 위험 지표가 없으면 `null`. 별도 문단으로 렌더 |

요청이 실패하면 **그 블록만 빼고 예보·위험은 그대로 보여준다**(§18-5).

**왜 단기 탭에서 분리했나** — 처음엔 `/short-term` 응답에 실었는데, LLM 동기 재시도가
탭 전체를 막아 화면이 **12초간 "불러오는 중…"으로 비는 것을 실측**했다. 예보는 이미
계산이 끝났는데 추천 때문에 전부 기다리는 구조였다. 분리 후에는 탭이 즉시 뜨고 추천
카드만 채워진다. 예보 재계산 비용은 캐시 히트라 0.02초로 무시할 수준이다.

**응답 지연을 만들지 않는다.** 그날 첫 조회는 규칙 문구를 즉시 저장·반환하고 다듬기는
`BackgroundTasks`로 넘긴다. Cloud Run은 응답 후 CPU를 스로틀링해 그 작업이 완주하지 못할
수 있어서, `is_llm=false` 행이 남으면 **다음 조회가 짧은 타임아웃(`advice_llm_timeout_s`,
기본 8초)으로 동기 재시도**한다. 캐시는 `daily_recommendation`의 `uq_daily` 멱등 upsert.

### 8.1 캐시가 그날 안에서 낡던 버그 (`0034`, 2026-08-04)

`uq_daily(user_farm_id, target_date)`가 키라 문구를 **하루에 한 번만** 만들었다. 그런데
단기예보는 발표 주기가 3시간이라 하루에 여덟 번 갱신된다:

```
05:00  첫 조회 → "앞으로 3일간 기상 위험 신호가 없습니다."  저장(is_llm=true)
14:00  새 발표분에 폭우 추가 → 날짜 카드에 강수 경고가 뜬다
       그런데 추천 카드는 여전히 "위험 신호가 없습니다"
```

**같은 화면에서 두 블록이 정면으로 모순한다.** 에러 없이 조용히 거짓말하는 부류라 §18-4에
걸리고, "선제적 안내"(PRD 철학 3)가 정작 필요한 순간에 실효된다.

`input_hash` 컬럼으로 판정한다. **지문 재료는 LLM 프롬프트를 결정하는 전부다** —
`프롬프트 버전 + 작물명 + 규칙 문구`(`app/services/advice_cache.py`). `polish()`가
`build_prompt(crop_name, base_text)` 하나를 넘기므로 결과를 바꾸는 것이 정확히 이 셋뿐이다.

그래서 이 지문은 **필요충분**하다:

- 문장이 달라지면 반드시 지문이 바뀐다(낡은 문구가 남지 않는다).
- 문장이 같으면 지문도 같다(같은 발표분 재조회에 LLM을 다시 부르지 않는다, §18-1).

**점수·등급을 넣지 않는 이유**가 여기서 나온다 — 문구에 한 글자도 안 들어가므로 넣으면
80.0 → 79.9에도 LLM을 헛되이 다시 부른다. 장기(§9)도 처음엔 월별 구조를 통째로 해시했다가
같은 이유로 이 함수로 통일했다.

기존 행은 `input_hash`가 NULL이라 다음 조회가 미스로 보고 한 번 다시 만든다 — backfill 불필요.

**토양 문단은 LLM을 태우지 않는다.** 매일 같은 내용이라 표현이 흔들릴 이유가 없고, 시비
조언은 문구가 고정돼 검증 가능한 편이 안전하다. 두 가지 제약이 걸려 있다:

- **말투가 "이 리는"이지 "회원님 밭은"이 아니다.** 값이 이 밭 실측이 아니라 동·리 토양검정
  표본 평균이라 밭을 단정하면 §18-4를 어긴다(같은 이유로 `SOIL_LIMITATION`을 고친 전례).
- **구체적인 시비량을 말하지 않는다.** 비료 표준사용량 API가 미연동이고 시비 시드도 없어
  근거가 없다 — 지어내는 대신 챗봇으로 넘긴다(챗봇은 RAG 근거가 있다, §13).

**실측으로 잡은 함정 2개** (2026-08-02, exaone3.5:7.8b):

1. **상대 날짜 환각** — 규칙 문구 "8월 2일"을 모델이 "모레까지"로 바꿔 하루가 어긋났다.
   원인은 few-shot 예시가 "모레(8월 3일)까지"로 날짜 상대화를 시연한 것. 오늘이 며칠인지
   모르는 모델이 날짜를 계산한 셈이라 §18-3 위반이다. → 제약조건에 금지 + 예시를 절대
   날짜로 교체. `RELATIVE_DATE_RULE` 상수를 테스트가 가리킨다.
2. **few-shot 작물 편중** — 챗봇 v5의 label bleed 전례가 있어 예시 3개의 작물을 처음부터
   분산했다(감자·오이·사과). 회귀 테스트로 과반을 막는다.

원칙(다른 LLM 기능에도 적용):
- 정형 사실을 명시적으로 나열하고 LLM에 계산을 맡기지 않는다(§18-3).
- 페르소나·대상·톤을 시스템 지시로 고정. 전문용어는 쉬운 표현 병기(원 의미 왜곡 금지).
- 프롬프트 템플릿은 코드에 흩지 말고 파일/상수로 버전 관리(CLAUDE.md §13).

## 9. 장기 커리큘럼 서술 (PRD §10-2, 구현 완료)

`app/prompts/long_term_advice.py` (`longterm-v1`) + `app/services/long_term_advice_service.py`.

**§8과 같은 구조다** — 규칙 문구가 품질 하한선, LLM은 다듬기만. 복제한 것이 아니라 문구
조립 헬퍼(`app/services/advice_text.py`: 받침 조사·경계 표현·소수 표기)를 **공유**한다.
두 탭의 말투가 갈리지 않게 하기 위해서다.

```
summarize_window()  월별 위험 → 값·허용구간 정형 요약  (순수, 기상만)
rule_advice()       정형 요약 → 규칙 문구              (순수, 분기 4개)
polish()            규칙 문구 → 다듬은 문구             (실패 시 None → 규칙 문구)
```

**FE 계약** — `GET /api/v1/farms/{id}/long-term-advice` (히트맵과 **별도 요청**, 이유는 §8과 동일):

```json
{ "text": "9월에 밤 기온이 2.1℃까지 내려가 …", "is_llm": true }
```

`soil_text`가 없다. 토양은 월별로 변하지 않아 3개월 어느 칸에서도 같은 말이 나오고,
단기 탭이 이미 같은 내용을 보여준다.

### 9.1 단기와 다른 점 — 어미를 규칙 문구 단계에서 못박는다

장기 점수는 예보가 아니라 **최근 5년 관측 평균 + 3개월전망 보정**이라 이론 추정치다.
"9월 야간 최저기온이 2.1℃로 허용 범위를 벗어**납니다**"로 단정하면 근사치를 확정 실측처럼
보여주는 것이라 §18-4를 정면으로 어긴다. 그래서 규칙 문구가 처음부터 "벗어**날 것으로
보입니다**"로 쓰고, 프롬프트는 **그걸 바꾸지 말라고만** 한다(`ESTIMATE_TONE_RULE`).

프롬프트 지시만으로 문체를 강제하지 않는 이유는 실측이다 — 챗봇 마크다운 별표를 프롬프트로
막으려는 시도가 **6회 전부 실패**했다(nexttodo.md). 결정론적으로 정할 수 있는 것은 코드에서
정한다.

`RELATIVE_MONTH_RULE`은 §8의 상대 날짜 금지와 같은 이유다 — 모델은 오늘이 몇 월인지 모르므로
"9월"을 "다음 달"로 바꾸면 계산을 한 셈이라 §18-3에 걸린다.

few-shot 3개는 배·상추·사과로, §8이 쓴 감자·오이·사과와 겹치지 않게 골랐다. 두 프롬프트를
합쳐 5작물이 고르게 나온다(label bleed 방지, 회귀 테스트가 겹침을 잡는다).

### 9.2 캐시가 밭당 1행이고 낡음은 지문으로 판정한다

단기의 `target_date` 같은 자연 키가 없다. 장기 창은 항상 오늘 기준이라 지난 창을 다시
보여줄 일이 없어(`PRD.md` §4.4) 밭당 1행으로 접는다 —
`long_term_recommendation`의 `uq_long_term(user_farm_id)` 멱등 upsert
(`DB.md` §3.17에 §3.14와 키 전략이 다른 이유를 적어뒀다).

낡음 판정은 **단기와 같은 지문 함수**를 쓴다(§8.1). 매월 23일 3개월전망이 발표되면 보정된
기온이 바뀌고, 그게 위험 판정이나 문구의 숫자를 바꾸면 지문이 달라져 자동으로 재생성된다.
바뀌지 않으면 재생성하지 않는다 — 그게 맞다.

실측상 이 지문은 밭당 **월 1~2회** 바뀐다. 즉 LLM 호출량이 밭 하나당 월 1~2회로 묶인다(§18-1).

### 9.3 생육기가 아닌 창에서는 LLM을 부르지 않는다

창 3칸이 전부 "생육기 아님/제철 아님"이면(예: 수확 끝난 감자밭) 서술할 데이터가 0이라
다듬게 하면 없는 관리 조언을 지어낸다. 규칙 문구로 끝낸다:

- 다음 생육기를 알 수 있으면 — "지금은 이 밭의 생육기가 아닙니다. 2027년 3월부터 다시 안내해 드릴게요."
- 알 수 없으면 — "…다시 파종하시면 그때부터 3개월 안내를 시작해 드릴게요."

두 번째 분기가 필요한 이유: 파종후경과일(`days_after_planting`) 기준 작물은 달력으로 다음
작기가 정해지지 않아 `next_season_month`가 `None`을 준다(의도된 동작). **5종 중 감자뿐**이다 —
오이·배는 `day_of_year`라 다음 작기가 잡힌다(실측: 오이밭 2026-12 조회 → "2027년 4월부터").

## 10. 품질 평가 (챗봇 "깎기")

- 예측 로직(결정론)과 LLM 답변 품질은 평가가 다르다. 답변은 루브릭으로: **충실성**(구조화 위험과 일치), **행동가능성**, **초보자 눈높이**, **수치 환각 없음**.
- (상황 → 기대 답변 특성) 골든셋 + LLM-as-judge로 자동 채점하며 프롬프트/모델 비교. 방법론은 `docs/methodology.md`(예정).

## 11. 상담 챗봇 엔드포인트 (FE 연동 계약)

`POST /api/v1/chat` — **SSE 스트리밍**(`text/event-stream`). `ApiResponse` 래퍼 안 씀(§6 스트리밍 예외).

**인증**: **필수**(2026-08-05 변경). `Authorization: Bearer <access>` 없거나 무효면 **401**이다.

> **⚠️ 변경 이력 — 게스트 모드는 없어졌다.** 종전에는 토큰이 없으면 게스트로 흘려보냈다.
> 두 가지 이유로 닫았다.
> 1. **명세 위반**: `PRD.md` §4.1이 "로그인 필수 / 비로그인 접근 시 로그인으로 리다이렉트"라고
>    적고 있고, §4.6(챗봇)에 게스트 조항은 없다. 게스트 경로는 구현 쪽에서 자란 것이다(§18-7).
> 2. **보안**: 인증 없이 GPU를 태울 수 있는 **유일한 엔드포인트**였다. 계정 없이 LLM 예산을
>    소진시킬 수 있었고, 프록시 뒤라 IP 기준 제한도 신뢰할 수 없다. 로그인을 요구하면 한도를
>    위조 불가능한 `user.id`로 걸 수 있다(`app/api/rate_limit.py`).
>
> **FE 영향**: 비로그인 화면(`/login`·`/signup`)에서 챗봇 진입점을 노출하면 안 된다 —
> `ChatDock`이 비로그인·세션 복구 중에는 렌더되지 않고, `/chat` 페이지는 `RequireAuth`로
> 감싸 로그인 화면으로 보낸다.

**레이트리밋**: 계정당 **분당 10턴**. 넘으면 `429` + `{"code": "RATE_LIMITED"}`.
스트림 시작 전 거절이라 일반 `ApiResponse` 실패 포맷으로 온다(§6).

**요청 본문**
```json
{
  "question": "지금 물 줘도 돼요?",       // 필수, 1~1000자
  "crop_id": 3,                          // 선택, 작물 한정. 밭이 잡히면 밭 작물로 자동 덮어씀
  "history": [                           // 선택. session_id를 주면 무시된다(서버 저장분이 진실)
    {"role": "user", "content": "..."},
    {"role": "assistant", "content": "..."}
  ],
  "farm_id": 12,                         // 선택, 특정 밭 기준 답변 원할 때(소유권 검증)
  "session_id": "8f3c...uuid4"           // 선택, 대화를 서버에 저장/이어가고 싶을 때
}
```

**대화 영속화(로그인 + `session_id`)**
- `session_id`는 **클라가 만든 uuid4**(대화 스레드 하나당 하나). 형식 검증: `^[0-9a-fA-F-]{8,64}$`.
- 로그인 상태 + `session_id`면 서버가 그 스레드의 히스토리를 **DB에서 로드/저장**한다 → 이때 body의 `history`는 **무시**(서버가 진실). FE는 새 요청에 `question`만 보내면 이어진다.
- 소유권은 `(user_id, session_id)`로 강제 — 남의 session_id를 넣어도 빈 히스토리만 나온다(정보 유출 없음).
- **성공한 턴만 저장**: 근거 없음 거절/LLM 오류 폴백 문구는 저장하지 않는다.
- `session_id`를 안 주면: 저장 없이 클라가 `history`를 들고 다니며 재전송(무상태). 로그인은
  어느 쪽이든 필요하다 — 저장 여부만 갈린다.

**밭 컨텍스트 동작(로그인 시)**
- `farm_id` 주면 그 밭(요청 유저 소유가 아니면 무시), 안 주면 유저 밭이 하나뿐일 때 그 밭.
- 밭이 잡히면: 밭 작물로 `crop_id` 자동설정 → **작물 되묻기 안 함**. `#회원 밭 정보`(작물·지역·파종 후 경과일·토양 추정치)를 프롬프트에 주입 → "내 땅 기준" 답변.
- 토양 수치는 **추정치**(실측 아님)로 표기. 생육단계 이름은 아직 매핑 미확정이라 **경과일(사실)만** 준다.

**응답 스트림**: `data: {"token": "..."}\n\n` 프레임 연속 → 종료 `data: [DONE]\n\n`. 오류/근거 없음은 서버가 폴백 문구로 흡수하고 반드시 `[DONE]`으로 끝맺는다(§18-5).

**FE 할 일**: 헤더에 access 첨부(**필수** — 없으면 401) + `credentials: "include"`(refresh 쿠키). 스트림을 `[DONE]`까지 읽어 토큰 이어붙이기. 대화를 서버에 저장/이어가려면 스레드마다 uuid4 `session_id`를 만들어 매 요청에 재전송(같은 대화 = 같은 값). 미저장 모드는 `history`를 직접 들고 다니며 매 요청 재전송. `429`(RATE_LIMITED)는 재시도가 아니라 안내 문구로 처리한다.

### 11.1 지난 대화 복원 — `GET /api/v1/chat/history`

`POST /api/v1/chat`이 저장은 하는데 **읽을 길이 없어서**, FE가 리로드할 때마다 새 uuid를 만들고 저장된 스레드는 고아가 됐다. 그래서 조회를 붙였다.

```
GET /api/v1/chat/history?session_id=<uuid4>
Authorization: Bearer <access>          // 필수 — 게스트는 저장 자체가 없다(없으면 401)
→ 200 { "success": true, "data": [ {"role":"user","content":"..."}, ... ], "error": null }
```

- `data`는 **오래된 순**, 최근 `chat_history_display_limit`(기본 100)개. 프롬프트에 넣는 6개 캡과 다른 값이다 — 모델이 참고할 양과 유저가 다시 읽을 양은 다르다.
- 소유권은 `POST`와 같은 `(user_id, session_id)` 스코프. 남의 스레드는 빈 배열.
- `session_id` 형식 위반은 422, 없는 스레드는 빈 배열(404 아님).

**FE 할 일**: `session_id`를 **유저별로 localStorage에 보관**(`chat_session:<userId>`)해 리로드/재방문에도 같은 스레드를 이어간다. 마운트 시 이 API로 화면을 복원하되, 실패하면 조용히 빈 대화로 시작(상담을 막지 않는다). 구현: `frontend/lib/chat.ts`의 `chatSessionId()`/`fetchChatHistory()`.

### 11.2 대화 스레드 목록/삭제 — 세션 테이블은 없다

```
GET    /api/v1/chat/sessions              → [{session_id, title, message_count, last_at}, ...]  최근 활동 순, 최대 30개
DELETE /api/v1/chat/sessions/{session_id} → 지운 메시지 수(0 = 없거나 내 것이 아님)
```

**`chat_session` 테이블을 만들지 않았다.** `chat_message`를 `session_id`로 묶으면 목록이 그대로 나오고, **새 대화는 클라가 uuid를 새로 만드는 순간 시작**되므로 서버가 미리 만들어 둘 행이 없다. 테이블을 두면 빈 스레드·고아 행·"메시지는 있는데 세션이 없음" 같은 정합 상태를 떠안게 된다.

- **제목**은 그 스레드의 첫 메시지(= 항상 첫 질문) 앞 30자. 저장하지 않고 조회 때 만든다.
- 목록 조회는 기존 인덱스 `ix_chat_message_user_session(user_id, session_id, id)`를 탄다 — 새 인덱스 없음.
- 삭제는 `user_id` 필터가 곧 소유권 검증이다. 남의 스레드는 404가 아니라 **0건**을 돌려준다(존재 여부를 알려주지 않는다).

**FE 할 일**: "새 대화" = `crypto.randomUUID()`로 새 키를 만들고 localStorage에 저장. 서버 호출 없음. 스레드 전환 시에는 `GET /chat/history`로 화면을 **덮어쓴다**(유저가 명시적으로 연 것이므로 복원 때와 달리 기존 메시지를 보존하지 않는다).

### 11.3 저장 용량과 보존 정책

실측(2026-08-04, 개발 DB):

| 항목 | 값 |
|---|---|
| assistant 답변 평균 | 907 바이트 |
| user 질문 평균 | 32 바이트 |
| **턴 1개(질문+답변) 실제 점유** | 본문 940B + 행 오버헤드 180B + 인덱스 160B ≈ **1.3 KB** |
| 퀘스트 로그(`user_daily_quest`) | 3행/유저/일 ≈ 300 B/일 |

하루 3턴 가정 시 연간 증가량:

| DAU | chat_message | user_daily_quest |
|---|---|---|
| 1,000 | 1.6 GB/년 | 0.1 GB/년 |
| 10,000 | 16 GB/년 | 1.1 GB/년 |
| 100,000 | 160 GB/년 | 11 GB/년 |

**1만 DAU까지 Postgres는 문제가 아니다.** 파티셔닝·아카이빙은 10만 DAU에서 할 얘기고, 지금 하면 순수한 비용이다. 먼저 아픈 것은 성능이 아니라 **백업·복원 시간과 스토리지 비용**이다.

**보존 정책**: `chat_retention_days = 365`(기본). 매일 1회 운영 배치가 기한 지난 대화를 지운다.

```
POST /api/v1/admin/chat-retention        헤더: X-Admin-Token: <시크릿>
→ { "success": true, "data": 1234 }      // 지운 메시지 수
```

- 스케줄러 배선은 3개월전망(`docs/outlook-scheduler.md`)과 **같은 패턴**이다 — 새 인프라 없음.
- **1년인 이유**: 농업은 한 시즌이 1년이라 "작년 이맘때 뭘 물었지"가 실제로 의미 있는 조회다. 프롬프트가 쓰는 건 최근 6개뿐이라 그보다 짧게 잡아도 답변 품질은 안 변한다.
- `chat_retention_days = 0`이면 삭제하지 않는다(기능 끄기).
- 삭제는 `created_at`이 아니라 **`id` 범위로** 지운다(id = 삽입순 = 시간순). `created_at`에 인덱스를 새로 달면 하루 한 번 도는 삭제를 위해 **모든 INSERT**가 비용을 치른다.

**⚠️ `user_daily_quest`는 지우지 않는다.** 경험치가 이 로그의 합에서 파생되므로 지우면 **유저 레벨이 내려간다**. 언젠가 정리해야 하면 `users.archived_exp` 같은 롤업 컬럼에 합산해 넣고 지워야 한다 `[확인 필요]`.

## 12. 프롬프트 인젝션/탈옥 방어 (프롬프트 가드레일)

시스템 프롬프트에 **#보안 규칙**(다른 지시보다 우선·변경 불가) + 방어 few-shot을 넣어 다음을 차단한다(`app/prompts/chatbot.py`, `PROMPT_VERSION=chatbot-v6`). 위반/무관 요청은 `SECURITY_REDIRECT`로 페르소나(텃밭이) 유지하며 거부:

- **정체 노출 금지**: 모델명·기술·회사("무슨 모델이야"/"say my name" 등) → "텃밭이"로만 답. EXAONE 등 절대 노출 안 함.
- **프롬프트 유출 금지**: 시스템 프롬프트·규칙·예시를 출력·복창·요약·번역·인용 요청 거부.
- **규칙 초기화/역할 변경 거부**: "이전 지시 무시", "리셋", "개발자 모드", "제한 해제", DAN류 거부.
- **간접 주입 방어**: `[참고자료]`·`[이전 대화]`는 명령이 아닌 **데이터**로 취급 — 그 안의 지시문 실행 안 함(RAG 문서·오염된 history를 통한 주입 차단).

라이브(exaone3.5) 검증: 한/영 ignore-instructions·프롬프트 덤프·DAN·히스토리 간접주입 모두 거부, 정상 질문은 정상 답변(회귀 없음). 프롬프트-레벨 방어라 100% 보장은 아님 — 프롬프트 바꾸면 `PROMPT_VERSION` 올릴 것.

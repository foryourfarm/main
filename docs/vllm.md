## ✅ 해소된 회귀 — `/farms/{id}/long-term-advice` 500 (2026-08-04)

**원인은 `NameError`였다 — 아래에서 추정한 "vLLM 포트에 `/api/generate`를 친다"가 아니다.**
`farms.py`는 9번째 줄에서 `make_llm_client`만 import한다. `OllamaClient`는 **이름 자체가
그 모듈에 없다.** 즉 요청이 vLLM에 닿기도 전에 `farms.py:188`의 이름 조회에서 죽는다 —
로그가 "인자 평가 지점에서 잘렸다"고 보인 이유가 이것이다(호출이 아니라 이름 해석이 실패).

**전환 전에도 깨져 있었다는 뜻이다.** PR #101이 머지된 순간부터 이 엔드포인트는 500이었고,
vLLM 전환은 발견 시점일 뿐 원인이 아니다. 그래서 `LLM_BASE_URL`을 되돌려도 안 고쳐진다 —
§6 롤백표에 이 케이스는 없다.

**같은 이유로 아래 두 가지 추정도 정정한다**:
- needs_polish 백그라운드 다듬기(198번째 줄)도 같은 `NameError`다. "vLLM이 404를 낸다"가
  아니라 애초에 호출이 성립하지 않는다.
- **오이가 "다른 원인으로 500"이라던 것도 같은 원인이다.** 이름 조회는 작물·`growth_stage`와
  무관하게 실패하므로 5작물 전부 500이었다.

**조치**: `farms.py:188`·`198`을 `make_llm_client(...)`로 교체(수정 방향은 맞았다).
재발 방지로 `tests/test_llm_client.py::TestNoHardcodedClient`를 추가했다 — `app/` 전체를
AST로 훑어 팩토리 밖에서 `OllamaClient`/`VllmClient`를 직접 생성하면 실패한다.
**기존 테스트 470개는 이 버그를 원리적으로 못 잡았다**(라우터 배선을 아무도 호출하지 않는다).

## 0. 지금까지 결론 (계속 갱신 — 최신 갱신: 2026-08-04 오전)

**결정된 것**:
- **vLLM 전환은 구조적으로 성공이다(§7 판정 유지).** Ollama의 "요청당 +7초 계단"이 vLLM
  continuous batching에서 "요청당 +0.7초"로 줄었다 — 10배 완만. 절대 수치("40초→6초")는
  프롬프트를 정직하게(잘리지 않고 다양하게) 재면 달라지지만, 방향은 안 바뀐다.
- **Qwen3 8B AWQ가 현재 선두 후보다** — 8B vs 14B **순수 비교**(같은 프롬프트·같은 스크립트,
  §11)에서 속도는 8B가 2~3배 빠르고, 품질(§9, 사실 보존 3회)은 **동률(둘 다 0/3 오류)**이다.
  지금까지 확인된 범위에서는 크기를 올려도 품질 이득이 안 보이고 속도만 깎였다.
- **Qwen3 생각 모드는 vLLM `chat_template_kwargs`로 실제로 꺼진다**(§9 하단, VM 실측
  완료·로컬 코드 반영, 아직 미커밋).
- **모델 교체 시 GPU 정리는 `nvidia-smi --query-compute-apps`로 PID를 특정해서 죽여야 한다.**
  `pkill -f`(자기참조로 SSH 세션째 죽음)·`fuser -k <port>`(vLLM의 EngineCore 자식 프로세스가
  포트를 안 쥐고 있어 고아로 남아 OOM 유발) 둘 다 오늘 실패로 확인됨.
  **`pgrep -f vllm`도 같은 자기참조 함정에 걸린다** — 진단 명령 자신의 cmdline에 그 문자열이
  들어 있어 항상 "살아 있음"으로 나온다. `pgrep -f "vllm[ ]serve"`처럼 써야 한다.
- **EXAONE 3.5 7.8B AWQ는 vLLM에서 뜬다(§2 해소). 그리고 품질에서 탈락했다(§9).** 로드에는
  `--trust-remote-code`가 필수이고, 띄운 뒤 프로덕션 프롬프트로 3회 재보니 **§9가 Ollama에서
  잡았던 자기모순 환각이 그대로 재현됐다**(3회 중 2회). 라이선스도 NC라 **후보에서 내린다.**
- **자동 채점만 믿으면 안 된다** — EXAONE은 사전 정의 오류 목록 기준 0/3 통과인데 답변을
  읽으면 2/3 실패였다(§9). 자동 채점은 1차 필터, 원문 읽기는 필수.

- **Gemma 3 12B도 탈락이다(§9).** EXAONE의 자기모순은 없지만 "두 사실 뭉개기"가 3회 중 2회,
  고유명사 왜곡 1건이고 **Qwen3를 이길 근거가 없다.** 속도(첫토큰이 14B 대역)·라이선스
  (Gemma Terms vs Apache 2.0)에서도 8B에 밀린다. **12~14B로 올려도 8B를 못 넘는다**는 관찰이
  Qwen3 14B에 이어 두 번째로 반복됐다.

- **✅ 모델 선정 종료 — `Qwen3/Qwen3-8B-AWQ`(`--served-model-name qwen3-8b`).** 네 후보를
  같은 조건(vLLM + `qwen14b_payload.json`)으로 재측정한 결과 8B만 5개 검사 항목이 전부 0이다
  (§9 "확정"). 속도도 1위(전체 완료 7.97s), 라이선스도 Apache 2.0으로 최선.
  **단서**: 8B는 답변이 짧아(57~95토큰) 근거의 부가 정보를 덜 담는다 — 환각을 안 하는 것과
  정보를 안 주는 것은 다르다(§9 **[확인 필요]**).
- **전환 시 `settings.llm_model`을 `qwen3-8b`로 맞춰야 한다**(§12 주의사항). 기본값이
  `exaone3.5:7.8b`라 그대로 두면 모델을 못 찾는다.

**아직 안 한 것**:
- `startup.sh` 영속화 — 최종 모델이 정해질 때까지 의도적으로 미뤘고, **이제 정해졌으므로
  다음 작업이다**(§8·§12).
- 품질 비교 표본 확장(지금은 질문 1개×3회, 5작물로 넓혀야 확정적). `bench_payloads.json`에
  5작물 6건이 이미 있으므로 새 파일 없이 가능하다.
- Kanana 1.5 8B·A.X-3.1-Light — Apache 2.0으로 라이선스는 좋지만 공식 AWQ가 없어 bf16
  시도가 필요하고 VRAM이 빠듯하다(§9 후보 확장) — 시간 남으면 위험 감수하고 시도.

## 1. 왜 바꾸는가 — 실측 기준선

로컬(RTX 5070 8GB, Ollama 0.31.1, `exaone3.5:7.8b`)에서 **실제 RAG 경로**로 쟀다.
검색은 미리 끝내고 생성만 동시에 던져 임베딩 경합을 변수에서 제거했다.

    단독 1건        첫토큰  3.6s | 총  9.7s | 447자
    동시 6건        첫토큰  4.5s | 총 10.9s
                    첫토큰 12.3s | 총 17.5s
                    첫토큰 19.2s | 총 24.4s
                    첫토큰 25.7s | 총 31.9s
                    첫토큰 33.0s | 총 38.8s
                    첫토큰 40.2s | 총 47.0s
                    >> 6건 전체 완료 47.0s

**첫토큰이 약 7초씩 계단식으로 늘어난다** — 병렬 처리가 아니라 거의 순차 처리다.
전체 47초 ≈ 단독 9.7초 × 5배. 원인은 `OLLAMA_NUM_PARALLEL`이 설정되지 않은 것이고
(`infra/ollama-vm/startup.sh`의 `override.conf`에 `OLLAMA_HOST`만 있다) VM도 같은 상태다.

**UX 판정**: 6번째 사용자는 질문 후 40초간 빈 화면을 본다. 프론트에 대기 순번 표시가 없어
"고장났다"고 판단할 시간이다. **첫토큰 이후는 6초라 빠르다 — 문제는 첫토큰까지다.**

> **대안을 먼저 검토했다**: `OLLAMA_NUM_PARALLEL=4` 한 줄로 완화될 가능성이 있었다
> (양자화 모델이 5.7GB뿐이라 L4 24GB에 KV캐시 여유가 크다). 팀 결정은 vLLM 전환이며
> (2026-08-04), 근거는 continuous batching이 계단식 대기를 구조적으로 없앤다는 것이다.
> 그 한 줄 시도는 **롤백 경로로 남겨둔다**(§6).

## 2. 확정된 사실 (추측 금지 — §3-4)

| 항목 | 확인 결과 | 출처 |
|---|---|---|
| vLLM의 EXAONE 지원 | **`ExaoneForCausalLM`** 아키텍처로 지원 | vLLM `docs/models/supported_models.md` |
| EXAONE 3.5 AWQ 양자화판 | **존재** — `LGAI-EXAONE/EXAONE-3.5-7.8B-Instruct-AWQ`, 4-bit W4A16g128 | HF 모델 카드 |
| 공식 기동 명령 | `vllm serve "LGAI-EXAONE/EXAONE-3.5-7.8B-Instruct-AWQ"` | 같은 모델 카드 |
| 라이선스 | **EXAONE AI Model License Agreement 1.1 - NC** (비상업) | 같은 모델 카드 |

**✅ 해소(2026-08-04, VM 실측) — 3.5 AWQ는 vLLM 0.26.0에서 로드된다. 단 `--trust-remote-code`가
필수다.** 위 표의 "공식 기동 명령"(모델카드 원문)을 그대로 쓰면 **가중치를 받기도 전에 죽는다**:

    pydantic_core._pydantic_core.ValidationError: 1 validation error for ModelConfig
      Value error, The repository ... contains custom code which must be executed
      to correctly load the model. Please pass the argument `trust_remote_code=True`

아키텍처 미지원이 아니었다. 리포의 `config.json`이 `auto_map`으로 커스텀 모델링 코드
(`configuration_exaone.py`)를 가리켜서, vLLM이 네이티브로 `ExaoneForCausalLM`을 알더라도
플래그 없이는 거부한다. **즉 모델카드의 기동 예시가 불완전하다** — 이 표의 "공식 기동 명령"
칸을 근거로 삼지 말 것. 실제로 쓸 명령은 §12에 있다.

플래그를 붙인 뒤 로드는 정상이었다:

    Resolved architecture: ExaoneForCausalLM
    quantization=auto_awq / Using MarlinLinearKernel for AutoAWQMarlinLinearMethod
    dtype=torch.float16, max_seq_len=8192 -> HTTP 200

**⚠️ `--trust-remote-code`는 HF 리포의 Python 코드를 VM에서 실행한다는 뜻이다.**
`LGAI-EXAONE`는 LG AI Research 공식 계정이고 Ollama로 이미 같은 모델을 쓰고 있어 이 전환이
새로 만드는 위험은 아니지만(선재 조건), 신규 VM·다른 모델에 이 플래그를 습관적으로 붙이지는
말 것. transformers도 로드 시 같은 경고를 남긴다("double-check they do not contain any
added malicious code").

**⚠️ 라이선스가 NC(비상업)다.** 지금 Ollama도 같은 모델을 쓰므로 vLLM이 새로 만드는 위험은
아니지만(선재 조건), 해커톤 밖으로 나가면 확인이 필요하다. **[확인 필요]**

## 3. VRAM — **반드시 AWQ로 가야 한다**

EXAONE 3.5 7.8B 구조(HF config): 32 layer · 8 KV head(GQA) · head_dim 128.
KV캐시 = `2(K,V) × 32 × 8 × 128 × 2B` = **토큰당 128 KiB**.

    ctx 8192 × 슬롯 1 = 1.1 GB
    ctx 8192 × 슬롯 4 = 4.3 GB
    ctx 8192 × 슬롯 6 = 6.4 GB
    ctx 8192 × 슬롯 8 = 8.6 GB

L4 = 24GB 기준 총량:

    구성    가중치  + KV(8192×6)  + bge-m3   = 합계    여유
    bf16     15.6     6.4          0.7        22.7    1.3GB   ← 위험
    AWQ       4.5     6.4          0.7        11.6   12.4GB   ← OK

**bf16으로 띄우면 여유가 1.3GB뿐이라 OOM 위험이 크다.** AWQ면 12.4GB가 남아 슬롯을 더 늘릴
여지까지 있다.

**참고 — Ollama가 이미 양자화판이다.** `ollama list`의 `exaone3.5:7.8b`는 4.8GB 파일이고
실측 VRAM 5.7GB다(`/api/ps`). 즉 "vLLM으로 바꾸면 더 무거워진다"가 bf16 기준으로는 사실이며,
AWQ를 써야 비슷한 수준을 유지한다.

**⚠️ AWQ의 트레이드오프**: L4는 Ada 세대라 W4A16을 잘 돌리지만, AWQ는 bf16보다 **단독 응답이
약간 느릴 수 있다.** 목표가 동시 6명 처리량이므로 방향은 맞지만, §7의 검증에서 단독 지연이
크게 나빠지지 않았는지 함께 본다.

## 4. 구조적 장애물 — 임베딩이 같은 주소를 쓴다

`embedding_client.py`가 **`settings.llm_base_url`을 그대로 쓴다**:

```python
self.base_url = base_url or settings.llm_base_url   # LLM과 같은 주소
```

즉 지금은 한 주소(`:11434`)로 생성·임베딩을 둘 다 부른다. **vLLM은 한 프로세스에 한 모델**이라
이 구조가 그대로 갈 수 없다.

### 선택지와 판단

| 방안 | 구성 | 판단 |
|---|---|---|
| **A. vLLM(생성) + Ollama(임베딩)** | vLLM `:8000` + Ollama `:11434` | **채택** |
| B. vLLM 단독(임베딩도 vLLM) | vLLM 인스턴스 2개 | ❌ 프로세스 수는 같은데 **재임베딩 위험만 추가** |
| C. 유지 | — | ❌ 동시성 미해결 |

**A를 택하는 결정적 이유는 재임베딩 회피다.** `embedding_client.py` docstring이 못박고 있다 —
*"`scripts/embed_corpus.py`가 적재 때 쓴 모델과 반드시 같아야 코사인 유사도가 의미를 가진다."*
Ollama bge-m3를 유지하면 **936청크를 다시 만들 필요가 없다.** vLLM의 bge-m3는 풀링·정규화가
다를 수 있어 검증 없이는 같은 벡터 공간이라고 단정할 수 없다.

## 5. 실행 순서 — 위험도 순으로 쪼갠다

### 1단계 — 임베딩 주소 분리 (위험 0, 서버 불필요)

`embedding_base_url` 설정을 새로 만들고 **기본값을 `llm_base_url`과 같게** 둔다.
→ **동작이 전혀 바뀌지 않는다.** vLLM 없이 머지 가능하고, 나중에 주소만 바꾸면 전환된다.
`test_env_example_matches_settings.py`가 env 이름 드리프트를 잡아준다(§17).

### 2단계 — `VllmClient` 구현 + 캔드 테스트 (위험 0, 서버 불필요)

`LlmClient` Protocol이 이미 있어 `generate`/`generate_stream` 두 개만 맞추면 된다.
Ollama와 다른 점:

| | Ollama | vLLM(OpenAI 호환) |
|---|---|---|
| 경로 | `/api/generate` | `/v1/chat/completions` |
| 입력 | `prompt` 문자열 | `messages` 배열 |
| 스트림 | JSON 줄마다 `response` | SSE `data: {...}` + `data: [DONE]` |
| 컨텍스트 창 | `options.num_ctx`(요청마다) | **`--max-model-len`(서버 기동 플래그)** |

**`num_ctx`를 요청으로 못 준다**는 점이 중요하다 — PR #97에서 고친 `llm_num_ctx=8192`가
vLLM에서는 **서버 기동 시 고정**된다. 클라이언트는 그 값을 검증만 할 수 있다.

검증은 실서버 없이 한다 — OpenAI 스트리밍 응답을 캔드 데이터로 넣어 파싱 테스트.
(현재 `OllamaClient`에는 그런 테스트가 없다. 새로 만드는 쪽에는 붙인다.)

### 3단계 — VM에 vLLM 병행 기동 (**진짜 위험 구간**)

`startup.sh`에 vLLM을 추가하고 **Ollama는 임베딩 전용으로 남긴다.**

확인 순서(앞이 실패하면 멈춘다):

1. **`ExaoneForCausalLM`로 3.5 AWQ가 실제 로드되는가** (§2의 미확정 항목)
2. `--max-model-len 8192` — PR #97의 `num_ctx`에 대응
3. `--gpu-memory-utilization` — Ollama 몫(bge-m3 0.7GB + 여유)을 남긴다. vLLM 기본은 0.9로
   **거의 전부 선점**하므로 반드시 낮춘다
4. `--max-num-seqs` — 동시 슬롯. §3 표로 6~8이 여유 범위
5. 워밍업 curl + `llm_timeout_s=90`이 vLLM 콜드로드에 충분한지 재확인
   (Ollama 콜드가 실측 67초였고 vLLM은 더 느릴 수 있다)

### 4단계 — 환경변수로 전환

`LLM_BASE_URL`을 `:8000`으로 바꾸면 전환, 되돌리면 롤백이다.
**재배포 없이 `gcloud run services update --update-env-vars`로 가능하다.**

> ⚠️ `--set-env-vars`를 쓰면 기존 환경변수 19개가 전부 삭제된다(README §⑤ 경고).
> 반드시 `--update-env-vars`를 쓴다.

## 6. 롤백

| 상황 | 조치 |
|---|---|
| vLLM이 로드 실패 | `LLM_BASE_URL`을 `:11434`로 되돌린다(Ollama는 계속 떠 있다) |
| 동시성이 기대만큼 안 나옴 | 같은 방법으로 되돌린 뒤 `OLLAMA_NUM_PARALLEL=4`를 시도(§1의 미시도 대안) |
| VRAM 부족 | `--max-num-seqs`·`--max-model-len`을 낮춘다. 그래도 안 되면 롤백 |

**Ollama를 끄지 않는 것이 롤백 전략의 핵심이다.** 임베딩 때문에 어차피 떠 있어야 하므로
생성 경로만 주소로 갈아타면 된다.

**⚠️ 다만 롤백에는 순서가 있다 — 주소를 되돌리기 전에 vLLM을 먼저 멈춰야 한다:**

```bash
gcloud compute ssh $VM --zone=$ZONE -- 'sudo systemctl stop vllm'
gcloud run services update <서비스> --update-env-vars LLM_BASE_URL=http://<VM_IP>:11434,LLM_BACKEND=ollama,LLM_MODEL=exaone3.5:7.8b
```

vLLM이 16.6GB를 쥔 채로 Ollama에 생성 요청이 들어오면 생성 모델 5.7GB를 올리다 L4 24GB가
넘쳐 OOM으로 죽는다(§8 3단계). **롤백 첫 요청은 콜드로드라 느리다**(실측 67초) — `llm_timeout_s`
기본값 90초 안에는 들어온다.

## 7. 검증 기준 — §1의 숫자와 같은 방법으로 비교

    항목                     Ollama(기준선)   vLLM 목표
    단독 첫토큰                3.6s           크게 나빠지지 않을 것(AWQ 트레이드오프)
    동시 6건 첫토클 최대       40.2s          **평탄해야 한다** — 계단식이면 실패
    동시 6건 전체 완료         47.0s          단축

**계단식(약 7초씩 증가)이 사라지는지가 성공 판정 기준이다.** continuous batching이 먹히면
첫토큰이 사용자 수에 비례해 늘지 않는다. 그게 안 나오면 전환 이득이 없으니 §6으로 되돌린다.

측정 스크립트는 §1과 동일한 방식(검색 미리 수행 + 생성만 동시 6건)으로 재사용한다.

**3단계에서 같이 해결한 것**:

- **휘발 위험 제거** — `nohup`/`setsid` 대신 **systemd 서비스**(`Restart=always`)로 넣었다.
  재부팅·Spot 재선점·크래시 복구를 OS가 해준다. 사람 손에만 있던 기동 플래그
  (`VLLM_USE_FLASHINFER_SAMPLER=0` 등)가 이제 코드에 있다.
- **§12의 "venv 설치 커맨드 기록 없음 → 재현 미확인"** — `if [ ! -x "$VLLM_ENV/bin/vllm" ]`
  가드 안에 `python3 -m venv` + `pip install vllm==0.26.0`을 넣어 신규 VM에서도 재현된다.
  기존 VM은 이미 venv가 있어 이 경로를 안 탄다.
- **⚠️ VRAM 충돌을 발견해서 같이 고쳤다** — 기존 `startup.sh`가 생성 모델을 `keep_alive:-1`로
  **VRAM에 상주**시키고 있었다. vLLM까지 올리면 넘친다:

        vLLM 가중치 5.0 + KV 11.6 = 16.6GB, bge-m3 0.7GB  -> 17.3GB (여유 6.7GB)
        + exaone 상주 5.7GB                                -> 23.0GB (OOM 위험)

  그래서 **생성 모델 워밍업을 없앴다**(`ollama pull`은 유지 — 디스크에만 둔다).
  **롤백 시 순서가 생긴다: `systemctl stop vllm`을 먼저 하고 `LLM_BASE_URL`을 되돌린다.**
  안 그러면 Ollama가 생성 모델을 올리다 OOM으로 죽는다(§6에 반영).

**아직 배포 안 됐다** — VM은 여전히 손으로 띄운 프로세스로 돌고 있다. 적용하려면 인스턴스
메타데이터의 startup-script를 갱신하고, 손으로 띄운 vLLM을 정리한 뒤 스크립트를 한 번 돌려야
한다(README §5).

### 1·2단계에서 확정된 것

- **동작은 아직 안 바뀐다.** 기본값이 `LLM_BACKEND=ollama`, `EMBEDDING_BASE_URL`이 비면
  `LLM_BASE_URL`을 쓴다. 실제 Ollama로 회귀 확인함(생성·임베딩 1024차원 정상).
- 호출부 3곳(`chat_service`, `farms.py` 2곳)이 `make_llm_client()`를 쓴다. 행동추천이 짧은
  타임아웃을 따로 주므로 팩토리가 `**overrides`를 통과시킨다.
- 모르는 `LLM_BACKEND` 값은 Ollama로 떨어지되 **경고를 남긴다** — 조용히 넘기면 "방어가 원인을
  감춘다" 패턴이 된다.
- 테스트 455 → **470**(신규 15개). vLLM SSE 파싱을 캔드 응답으로 고정했다. **파싱이 틀려도
  예외가 안 나고** 빈 답변 → `LLM_ERROR_TEXT` 폴백으로만 보이기 때문이다.

## 9. 모델 선택 — 재검토 (2026-08-04)

EXAONE은 "지금 Ollama가 쓰던 모델"이라는 이유로 이어진 것이고, vLLM으로 갈아타는 참에 더 나은
후보가 있는지 함께 본다.

### 기존 벤치마크는 품질 평가가 비어 있었다

[`llm-benchmark-eval.md`](./llm-benchmark-eval.md)가 EXAONE 3.5 7.8B vs Qwen3 8B를 3회씩
돌렸지만 **`평가: ㅁ` 칸이 전부 미기입이다.** 즉 EXAONE 선택의 실제 근거는 품질이 아니라
**Qwen3의 운영 문제**였다:

- Qwen3는 기본이 "생각 모드"라 `think:false` 없이는 토큰 예산을 내부 사고에 다 쓰고 **응답이
  빈 문자열**로 나온다(300토큰 캡에서 0자 실측).
- `/api/generate`(raw)로 부르면 한국어 질문에 영어로 되묻는 오작동. `/api/chat` + 정식 chat
  template에서만 정상.

**vLLM에서는 이 두 문제의 성격이 바뀐다** — `/v1/chat/completions`가 chat template을 적용하고,
생각 모드는 `chat_template_kwargs`로 끌 수 있다. 즉 **Qwen3 배제 근거가 약해진다.**

### 그 벤치마크 답변에서 EXAONE의 환각을 발견했다

근거 원문: *"탄저병 방제를 위하여 **6월 상순**부터 **10일 간격**으로 적용농약을 살포한다."*

    답변 1: "6일 간격으로 적용농약을 살포"        -> 10일 -> 6일  (환각)
    답변 2: "6월 중순부터 시작하여 10일 간격"     -> 상순 -> 중순 (환각)
    답변 3: "6월 상순부터 시작하여 10일 간격"     -> 정확

**3회 중 2회가 근거의 숫자를 바꿨다.** 평가란이 비어 있어 아무도 짚지 않았다. 농약 살포 간격은
초보 귀농인에게 그대로 행동으로 옮겨지는 수치라 **가장 위험한 종류의 환각**이다(§18-4, PRD 철학 1).

이건 2026-08-04에 별도로 관찰한 것과 같은 계열이다 — 상추 답변에 근거 없는 "염분 과다"가
들어갔고, 오이 접목에 "수확량 증대·기후 적응력"이 붙었다(둘 다 근거 0건).

### 선택 기준 — 속도가 아니라 충실성이다

| 기준 | 왜 |
|---|---|
| **근거 충실성**(숫자 보존) | 위 환각이 제품 신뢰를 직접 깎는다. **1순위** |
| 지시 준수 | 보안 규칙·작물 한정·마크다운 금지를 지키는가(EXAONE은 마크다운 금지 6회 전부 위반) |
| 라이선스 | EXAONE 3.5 = **NC(비상업)**. Qwen3 = Apache 2.0 |
| VRAM | L4 24GB에 KV캐시(6슬롯 6.4GB) + bge-m3 0.7GB를 남겨야 한다(§3) |
| 속도 | 이미 충분하다(50 tok/s, 답변 350~450토큰 = 7~9초). **병목은 동시성이지 단독 속도가 아니다** |

**속도를 1순위로 두지 않는 이유**: §1 실측에서 단독 응답은 9.7초로 문제가 없었고, 문제는 6명
동시에서 큐가 직렬이라는 것이었다. 그건 모델이 아니라 **런타임(vLLM)이 푸는 문제**다.

### 후보와 판단 상태

| 후보 | 라이선스 | vLLM 지원 | 상태 |
|---|---|---|---|
| EXAONE 3.5 7.8B (현행) | **NC** | `ExaoneForCausalLM` + AWQ 존재 | 환각 실측됨(위) |
| Qwen3 8B | Apache 2.0 | 지원 | 배제 근거가 vLLM에서 약해진다 — **재평가 대상** |
| EXAONE 4.0 32B | NC | `Exaone4ForCausalLM` | L4에 32B는 AWQ여도 빡빡 — **[확인 필요]** |

**⚠️ 다른 한국어 모델(Kanana·A.X·HyperCLOVA SEED·Midm 등)은 블로그 수준 정보만 확인돼 근거로
쓰지 않았다**(§3-4). 채택을 검토하려면 vLLM 지원 아키텍처와 라이선스를 1차 출처로 확인해야 한다.

### 결정 방식 — 비어 있던 평가란을 자동 채점으로 대체한다

기존 벤치마크가 실패한 이유는 **사람이 채워야 하는 주관 평가란**이었기 때문이다. 대신 **객관적·
자동 채점 가능한 기준**으로 바꾼다:

- 근거에 있는 수치(`6월 상순`, `10일 간격`)를 **보존했는가**
- 근거에 없는 수치 변형(`6일 간격`, `6월 중순` 등)을 **만들지 않았는가**

같은 프롬프트(`build_chat_prompt`)·같은 RAG 근거·같은 옵션(`num_ctx=8192`)으로 모델만 바꿔
3회씩 돌린다. 이 방식은 재현 가능하고, 코퍼스가 바뀌어도 다시 돌릴 수 있다.

**모델 교체가 임베딩을 건드리지 않는다는 점이 중요하다** — bge-m3는 그대로이므로 `knowledge_chunk`
936개를 재적재할 필요가 없다(§4). 즉 생성 모델 교체는 되돌리기 쉬운 결정이다.

### 실측 — Qwen3가 충실성에서 낫다 (2026-08-04)

같은 프롬프트(`build_chat_prompt`)·같은 RAG 근거·같은 옵션(`num_ctx=8192`, `num_predict=768`,
`temperature=0.4`)으로 모델만 바꿔 3회씩. 질문 *"사과 탄저병 방제는 언제부터 며칠 간격으로
하나요"*, 근거의 정답은 **6월 상순 / 10일 간격**.

    exaone3.5:7.8b   #1 정답보존 O  오류 ['6월 중순']  140토큰 43tok/s
                     #2 정답보존 O  오류 없음          122토큰 44tok/s
                     #3 정답보존 O  오류 없음          113토큰 43tok/s
                     -> 3회 중 1회 오류

    qwen3:8b         #1 정답보존 O  오류 없음           69토큰 36tok/s
                     #2 정답보존 O  오류 없음           69토큰 41tok/s
                     #3 정답보존 O  오류 없음           77토큰 40tok/s
                     -> 3회 중 0회 오류

**EXAONE `#1`이 특히 나쁜 형태다** — 근거를 정확히 인용한 **바로 다음 문장에서** 스스로 틀린
값을 만든다:

> "6월 상순부터 시작하여 10일 간격으로 적용농약을 살포하는 것이 권장됩니다. **따라서 방제 시작
> 시기는 6월 중순경이 적당하며**, …"

초보자는 결론 문장을 행동으로 옮긴다. 앞에 정답이 있어도 뒤에서 뒤집으면 무의미하다.

**Qwen3는 답변이 짧고(69~77토큰 vs 113~140) 3회가 거의 동일하다** — 사실 기반 응답에서 일관성은
장점이다. 다만 짧은 것이 항상 좋은지는 별개 질문이다(정보 누락 가능성).

**⚠️ 이 측정의 한계**:
- **1개 질문 × 3회다.** 방향은 보이지만 확정하기엔 표본이 작다. 5작물로 넓히면 더 신뢰할 수 있다.
- 자동 채점은 **미리 정한 오류 목록**(`6일 간격`·`6월 중순` 등)에 걸리는 것만 잡는다. 목록 밖의
  환각은 놓친다.
- Ollama 경로 측정이다. vLLM에서 chat template이 달라지면 거동이 바뀔 수 있다.
- 이 측정에서 Qwen3는 `/api/chat` + `think:false`로 불렀다. **vLLM에서는 생각 모드를
  `chat_template_kwargs`로 꺼야 하고, 그게 실제로 먹히는지는 미확인이다 — [확인 필요]**.

**→ 잠정 결론**: 라이선스(Apache 2.0 vs NC)와 충실성 양쪽에서 **Qwen3 8B가 유리하다.** 다만
표본이 작아 5작물로 확장 측정한 뒤 확정할 것을 권한다. 교체 비용은 낮다(임베딩 불변, env 전환).

### 실측 — Qwen3-14B-AWQ, **실제 vLLM + 프로덕션 프롬프트**로 재확인 (2026-08-04)

위 실측(§9 "Qwen3가 충실성에서 낫다")의 한계 두 개를 이번에 같이 없앴다 — "Ollama 경로였다"와
"vLLM `chat_template_kwargs`가 실제로 먹히는지 미확인"이다. `build_chat_prompt()`를 **직접
import해서 호출**했다(손으로 프롬프트를 흉내내지 않음 — 처음 한 번은 근거 없이 맨 질문만
던졌다가 모델이 탄저병을 "뿌리혹병"이라 부르는 환각이 나와서, 그게 프롬프트 문제였음을 먼저
확인하고 바로잡았다). 같은 질문·같은 근거 3청크, `qwen3-14b`(§9 후보 확장의 1순위)로 3회:

    qwen3-14b (vLLM)  #1 정답보존 O  오류 없음  115토큰  finish=stop
                       #2 정답보존 O  오류 없음  104토큰  finish=stop
                       #3 정답보존 O  오류 없음  121토큰  finish=stop
                       -> 3회 중 0회 오류 (qwen3:8b Ollama 실측과 동률)

**핵심 수치("6월 상순부터 10일 간격")는 3회 다 원문 그대로다.** §9의 사전 정의 오류 목록
(`6일 간격`·`6월 중순` 등)에도 안 걸렸다.

**⚠️ 다만 새로운 패턴 하나 — 두 사실을 하나로 합친다.** #2·#3이 "7월 상순부터 8월 하순까지"라고
했는데, 근거는 "7월 상순 **최초 발생**"과 "7월 하순~8월 하순 **많이 발생**"을 구분해서 적었다.
새 숫자를 지어낸 건 아니라 자동 채점(사전 정의 오류 목록 방식)은 통과하지만, 서로 다른 두
사실을 하나의 구간처럼 뭉갠 것이다 — §9가 이미 적어둔 자동 채점의 한계("목록 밖의 환각은
놓친다")가 바로 이런 걸 말한다. 사람이 한 번은 봐야 한다.

**곁들여 확인된 것**: `prompt_tokens=1983` — 이번 3청크짜리 프로덕션 프롬프트의 실제 토큰수다.
§11의 3,189자(잘린 프롬프트)와는 다른 값이니 섞어 쓰지 말 것. `finish_reason=stop`(전부
`length`가 아니라 정상 종료)도 §11이 지적한 "출력이 짧게 잘려 완료시간이 낙관적으로 나왔다"는
우려와 무관한 별개 측정임을 보여준다 — 이건 응답이 다 나오고 자연스럽게 멈췄다.

**→ 이 결과로 §9 잠정 결론이 한 단계 더 굳어졌다.** Qwen3 계열(8B·14B 둘 다)이 이 질문에서
EXAONE보다 안정적이고, **14B로 올려도 8B의 장점(충실성)이 유지된다** — 크기를 올린다고
공짜로 나빠지지 않았다. 다만 여전히 **질문 1개 × 3회**라 §9가 이미 적어둔 한계(5작물로
확장 필요)는 그대로 남는다.

### 실측 — EXAONE 3.5 7.8B AWQ, vLLM에서 재확인 (2026-08-04) — **환각 패턴이 재현됐다**

§9가 남긴 한계 *"Ollama 경로 측정이다. vLLM에서 chat template이 달라지면 거동이 바뀔 수
있다"* 를 해소한 측정이다. **같은 `qwen14b_payload.json`**(§11 재측정에서 쓴 그 파일, 같은
질문·같은 근거 3청크)로 모델만 바꿔 3회. 정답은 **6월 상순 / 10일 간격**.

    exaone35-7.8b (vLLM)  #1 정답보존 O  자동채점 오류 없음  154토큰  finish=stop
                          #2 정답보존 O  자동채점 오류 없음  176토큰  finish=stop
                          #3 정답보존 O  자동채점 오류 없음  173토큰  finish=stop
                          -> 자동 채점으로는 0/3 오류. **사람이 읽으면 2/3 실패다.**

**자동 채점(사전 정의 오류 목록)은 3회 다 통과한다.** `6일 간격`·`6월 중순` 같은 등록된
오류 문자열이 안 나왔기 때문이다. 그런데 답변을 읽으면 **#1·#2가 자기가 방금 인용한
"10일 간격"을 바로 다음 문장의 예시에서 스스로 어긴다**:

    #1  "...10일 간격으로 살포하는 것이 권장됩니다. 예를 들어, 6월 10일부터 시작하면
         6월 20일, 7월 10일, 8월 10일 등으로 일정하게..."
         -> 간격이 10일 -> 20일 -> 한 달로 벌어진다. 자기 문장과 모순.

    #2  "...약 10일 간격으로 살포하는 것이 권장됩니다. 예를 들어, 6월 10일부터 시작한다면
         다음 살포 예정일은 약 20일 후인 6월 30일 정도가 될 것입니다."
         -> "10일 간격"이라 해놓고 다음 살포일을 20일 후로 잡는다.

**§9가 Ollama `/api/generate`에서 관찰한 그 패턴과 정확히 같은 형태다** — 근거를 옳게 인용한
직후 스스로 뒤집는다. 다만 위치가 옮겨갔다: Ollama 때는 결론 문장("따라서 6월 중순경이
적당하며")이 틀렸고, 이번엔 **구체적 살포 달력 예시**가 틀렸다. 초보자에게는 후자가 더
위험하다 — 날짜가 적혀 있으면 그대로 달력에 옮겨 적는다.

**추가로 발견 — 같은 근거·같은 질문인데 #2와 #3이 정반대 지시를 한다.**

    #2  "병든 과실은 신속히 제거하여 땅에 묻는 것이 중요합니다."
    #3  "병든 과실은 즉시 따내어 땅에 묻지 않고 적절히 처리하는 것이 중요합니다."

최소 하나는 근거 왜곡이다(어느 쪽이 근거인지는 청크 원문 대조가 필요 — **[확인 필요]**).
자동 채점은 이런 상반된 지시를 잡을 수단이 아예 없다.

**#3은 §11이 14B에서 지적한 "두 사실 뭉개기"도 재현한다** — "초기 발생 시기인 7월 상순부터
8월 하순까지"는 근거의 "7월 상순 최초 발생"과 "7월 하순~8월 하순 많이 발생"을 한 구간으로
합친 것이다. 즉 이 패턴은 특정 모델의 버릇이 아니라 **모델 공통**일 가능성이 있다.

**→ 판정: EXAONE 3.5는 후보에서 내린다.** vLLM에서도 환각이 재현되고(§9 배제 근거가 약해지긴
커녕 굳어졌다), 라이선스도 NC(비상업)라 Qwen3(Apache 2.0)에 밀린다. Qwen3 8B·14B는 같은
페이로드에서 이런 자기모순이 0회였다.

**⚠️ 이 측정에서 배운 방법론 하나 — 자동 채점만으로는 부족하다.** §9가 "목록 밖 환각은
놓친다"고 적어둔 한계가 이번엔 **결과를 정반대로 뒤집는 수준**이었다(0/3 통과 vs 2/3 실패).
앞으로 후보를 볼 때는 자동 채점을 1차 필터로만 쓰고 **답변 원문을 반드시 읽는다.**

**곁들여 — `prompt_tokens`가 모델마다 다르다.** 같은 페이로드인데 14B는 1983, EXAONE은
**1530**이다. 토크나이저가 다르니 정상이며, 토큰 수를 모델 간 비교 지표로 쓰지 말 것.

### 실측 — Gemma 3 12B(w4a16), vLLM (2026-08-04) — **EXAONE보다 낫고 8B는 못 이긴다**

`RedHatAI/gemma-3-12b-it-quantized.w4a16`, 같은 `qwen14b_payload.json`으로 3회.
`chat_template_kwargs`(Qwen3용)를 그대로 실어도 **오류 없이 무시된다**(EXAONE과 동일 — 기본
`True`로 둬도 안전하다는 §9 하단 판단이 세 번째 모델에서도 확인됐다).

    gemma3-12b (vLLM)  #1 정답보존 O  뭉개기 O  106토큰  finish=stop
                       #2 정답보존 O  **뭉개기 없음(유일)**  115토큰
                       #3 정답보존 O  뭉개기 O + 고유명사 왜곡  100토큰

    검사 항목                     EXAONE 3.5 7.8B   Gemma 3 12B
    정답 보존(6월 상순/10일 간격)  3/3               3/3

**Gemma는 EXAONE의 치명적 결함(자기모순)이 없다.** "10일 간격"이라 해놓고 예시에서 20일을
드는 식의 자기부정이 3회 다 없었다.

**#2는 지금까지 어떤 모델도 못 한 것을 해냈다** — 근거의 두 사실을 정확히 구분해 인용했다:

> "7월 상순경에 **처음 발생**하고 7월 하순~8월 하순경에 **많이 발생**하므로 6월 상순부터…"

§11이 Qwen3 14B에서, §9가 EXAONE #3에서 지적한 "뭉개기"를 이 답변만 피했다. **그런데 같은
모델의 #1·#3은 똑같이 뭉갰다**("7월 상순부터 8월 하순까지 많이 발생"). 능력이 없는 게 아니라
일관되지 않다 — 3회 중 1회만 정확한 구분을 한다.

**#3에 고유명사 왜곡이 있다** — "아카**리아**나무"(#1·#2는 "아카시아나무"로 정확). 수치가
아니라 자동 채점 목록에 없고, 초보자가 검색하면 아무것도 안 나오는 단어를 준다.

**✅ EXAONE의 `[확인 필요]`(땅에 묻어라 vs 묻지 마라)가 사실상 해소** — Gemma 3회 전부와
EXAONE #2가 "병든 과실은 따내어 **땅에 묻는다**"로 일치한다. EXAONE #3의 "땅에 묻**지 않고**"가
왜곡 쪽이다. (청크 원문 직접 대조는 아직이므로 **정황 근거**로 기록한다.)

**→ 판정: 채택하지 않는다.** 품질은 EXAONE보다 명확히 낫지만 **Qwen3를 이길 근거가 없고**,
속도(첫토큰이 14B 대역, tok/s는 EXAONE의 절반)와 라이선스(Gemma Terms vs Apache 2.0) 양쪽에서
Qwen3 8B에 밀린다. 12~13B로 올려도 8B를 못 넘는다는 §11의 관찰(14B 사례)이 다른 계열에서도
반복됐다.

`#1`은 "6월 상순부터 10일 간격" 뒤에 "꾸준한 관리가 필요해요"로 끝난다. 근거에 있던
**중간기주(아카시아·호두나무) 제거 · 병든 과실 처리 · 봉지 씌우기를 전부 안 다뤘다.**
다른 모델들이 그 대목을 다루다 뭉갠 것과 비교하면, 8B는 뭉개기를 **회피한 게 아니라 그
주제를 건드리지 않았다.** 환각을 안 하는 것과 정보를 안 주는 것은 다르다 — §9가 처음부터
적어둔 "짧은 것이 항상 좋은지는 별개 질문(정보 누락 가능성)"이 바로 이 지점이다.
**[확인 필요]** — 근거의 부가 정보를 얼마나 담아야 적정한지는 이 측정으로 못 정한다.

**약한 흠 1건**: `#2`의 *"병원균이 활발히 번식하는 시기와 **일치하도록** 꾸준히 살포"* —
6월 상순 방제는 발생기(7~8월) **전에** 치는 선제 조치인데 "일치"라고 하면 인과가 어긋난다.
새 수치를 지어내진 않아 자동 채점은 통과한다(또 하나의 목록 밖 사례).

**→ 최종 결정: `Qwen3/Qwen3-8B-AWQ` (`--served-model-name qwen3-8b`).** 충실성 1위(동률
없음), 속도 1위, 라이선스 Apache 2.0. **12~14B로 올리면 속도만 깎이고 품질은 안 는다**는
관찰이 서로 다른 계열(Qwen3 14B · Gemma 3 12B)에서 두 번 반복됐다.

### ⚠️ 방법론 구멍 — 선두 후보만 다른 조건에서 쟀다 (2026-08-04) — **위에서 해소됨**

    모델           품질 측정 조건
    Qwen3 8B      **Ollama /api/chat + 구 페이로드**   <- 조건이 다르다
    Qwen3 14B     vLLM + qwen14b_payload.json
    EXAONE 3.5    vLLM + qwen14b_payload.json
    Gemma 3 12B   vLLM + qwen14b_payload.json

도전자 셋은 같은 조건에서 쟀는데 **정작 채택하려는 8B만 다른 런타임·다른 페이로드 측정이다.**
§9가 "Ollama 경로라 vLLM에서 거동이 바뀔 수 있다"고 적어둔 한계가 **선두 후보에만 그대로
남아 있다.** EXAONE에서 그 한계를 해소해보니 거동이 안 바뀌긴 했지만, 그건 EXAONE의 결과지
8B의 보증이 아니다.

**8B를 같은 조건(vLLM + `qwen14b_payload.json`)으로 3회 재측정한 뒤에 확정할 것.** 모델
가중치가 VM에 이미 있어 비용이 낮다. 같이 `bench.py`도 돌려 **청크수를 기록**하면 네 모델을
tok/s로 나란히 비교할 수 있다(§11의 `[확인 필요]` 해소).

"Ollama에 이미 있다"는 후보 조건이 아니다. **vLLM 지원 아키텍처 + 양자화 체크포인트 + L4 적재 +
라이선스** 네 가지를 다 통과해야 후보다. 1차 출처로 확인한 결과:

**탈락시킨 것**:
- `llama3` — Llama 커뮤니티 라이선스 + 한국어가 위 둘보다 약하다(리포에 측정 기록 없음).

- EXAONE 4.0 32B — L4에 AWQ여도 KV캐시까지 넣으면 빡빡하다. **[확인 필요]**이지만 후순위.

플러그인 없이도 될 가능성이 있다 — 시도해서 확인할 것.

**Gemma 3는 라이선스가 EXAONE의 NC와 같은 종류의 주의가 필요하다** — "Gemma Terms of Use"가
금지행위정책(Prohibited Use Policy)을 참조하고 구글이 원격으로 사용을 제한할 권리를 명시한다.
Apache/MIT급 자유도가 아니다.

**정정 (2026-08-04, 모델카드 1차 확인)** — 위 표의 Gemma 3 행에 부정확한 항목이 셋 있었다:

- **"커뮤니티 AWQ"가 아니라 GPTQ 기반 w4a16이다.** 채택 후보 `RedHatAI/gemma-3-12b-it-quantized.w4a16`

  **§3·§11의 "AWQ끼리 비교" 프레임에 그대로 넣으면 안 된다.**

### 로컬 다중 모델 비교는 하드웨어 때문에 실패했다 (기록)

4모델 × 5문항 × 2회로 넓히려 했으나 **첫 모델 이후 진행이 멈췄다.** 원인은 로컬 GPU가 8GB인데
`keep_alive:-1`로 여러 모델을 동시 상주시키려 한 것이다(exaone 5.7GB 하나로 이미 8GB 중 5.6GB).
**L4 24GB와 무관한 로컬 제약**이라 측정 방식의 결함이지 모델의 문제가 아니다.

→ 확장 측정은 **VM(L4)에서, vLLM으로 후보 2개만** 돌리는 것이 맞다. 로컬에서는 모델을 하나씩
`keep_alive`를 짧게 주고 순차로 돌려야 한다.

## 10. 미해결 / 확인 필요

- **[확인 필요] EXAONE 라이선스 NC(비상업)** — 해커톤 범위 밖 사용 시 재검토. **다만 §9에서
  품질로 탈락시켰으므로 실무상 쟁점이 아니게 됐다.**
- **✅ 해소 — vLLM 0.26.0에서 3.5 AWQ는 로드된다**(§2). `--trust-remote-code` 필요.
- **[신규·확인 필요] 같은 근거·같은 질문 3회에서 상반된 지시가 나왔다** — EXAONE #2 "병든
  과실을 땅에 묻어라" vs #3 "땅에 묻지 마라"(§9). 어느 쪽이 근거인지 청크 원문 대조가 필요하고,
  **다른 모델도 같은지 봐야 한다**(모델 문제인지 근거 문제인지 안 갈렸다).
- **[신규] 자동 채점 방식의 신뢰도가 낮다** — §9의 사전 정의 오류 목록 방식이 EXAONE의
  자기모순(인용 직후 예시에서 간격을 어김)을 전부 통과시켰다. 후보 평가 시 원문 읽기를
  절차에 포함할 것.
- **✅ 해소 — §11 잠정치를 실제 프롬프트로 재측정함**(§11 "재측정" 하위 절). 계단식 완화는
  재확인됐지만 절대 수치(첫토큰·prefix cache 히트율)는 처음 값보다 나빠졌다 — 처음 값을
  인용하지 말 것. 다만 모델도 8B→14B로 같이 바뀌어 순수 비교는 아직 아니다(아래 항목).
- **✅ 해소 — 8B를 같은 조건으로 재측정함**(§11 "순수 비교" 하위 절). 속도는 8B가 약
  2~3배 빠르고 품질(§9)은 동률 — 지금까지 확인된 범위에서는 8B 쪽으로 기운다.
- **[신규] 모델 정리 절차가 세 번 바뀌었다** — `pkill -f`(자기참조로 실패) →
  `fuser -k 8000/tcp`(EngineCore 자식이 고아로 남아 실패, OOM 유발) →
  `nvidia-smi --query-compute-apps`로 PID 특정 후 `kill -9`(성공). vLLM V1은
  APIServer·EngineCore가 별 프로세스라 **포트 기반 정리로는 부족하다.** `startup.sh`
  영속화 때 재기동/교체 스크립트에 이 방식을 표준으로 넣을 것.
- **`startup.sh`가 아직 Ollama 전용이다.** VM의 vLLM 기동은 사람이 SSH로 손으로 한 것이라
  재부팅·Spot 재선점에 사라진다. `VLLM_USE_FLASHINFER_SAMPLER=0` 등 우회 플래그도 명령줄에만
  있다 — **재현 가능한 상태가 아니다.**
- `OllamaClient`에 파싱 테스트가 없다 — 2단계에서 `VllmClient`에는 붙이지만, 기존 쪽은
  그대로 남는다(별건).

## 11. 동시성 실측 — VM(L4), vLLM Qwen3 8B AWQ (2026-08-04)

§7이 요구한 "VM에서 재측정"을 손으로 띄운 vLLM에 대해 처음 수행했다. **§1과 같은 방법
(검색 미리 수행 + 생성 동시 6건)** 은 아니고 별도 벤치 스크립트로 쟀다 — §7 기준과 직접
비교하려면 같은 스크립트로 재측정 필요(아래 한계 참고).

    항목              Ollama(§1 기준선)   vLLM(Qwen3 8B AWQ, L4)
    동시 6건 첫토큰    4.5 → 40.2s(계단식) 0.53 ~ 2.52s (계단 없음)
    동시 6건 전체 완료 47.0s              6.47s
    prefix cache 히트  기능 없음           **61~88%**
    임베딩(참고)       로컬 2.55s          0.34s(vLLM 임베딩 서버, bge-m3 아님 — §4 결정과 무관)

**§7의 성공 판정("계단식이 사라지는가")을 통과한다** — 6건 동시에도 첫토큰이 사용자 수에
비례해 늘지 않는다. continuous batching이 실제로 먹힌다는 뜻이고, 이게 vLLM 전환의 핵심
가설이었다(§1).

**⚠️ 이 숫자는 낙관적이다 — 조건 두 개가 실제 운영과 어긋났다:**

1. **프롬프트가 3,189자였다(실제 RAG 프롬프트는 5,764자).** heredoc이 붙여넣기 과정에서
   깨져 근거 생성부가 잘렸다. 실제 크기면 prefill이 더 걸린다.
2. **출력이 38~153토큰이었다(실제 답변은 177~444토큰, §9 참고).** 잘린 프롬프트라 근거가
   무의미한 반복문이었고 모델이 할 말이 없었다 — 완료 6.47초는 그만큼 짧게 나온 결과다.

**결론이 바뀔 가능성은 낮다고 본다** — 계단이 사라진 것과 캐시가 60~88% 먹는 것은 프롬프트
크기와 무관한 **구조적** 개선이다(continuous batching + prefix caching은 요청 길이가 아니라
동시 요청 수·공통 접두어 비율에 반응한다). 오히려 프롬프트가 커지면 시스템 프롬프트·RAG
공통부의 캐시 재사용률이 더 올라갈 개연성이 크다. 다만 **정확한 절대값은 재측정 전까지
잠정치다** — §7 판정("성공")은 유지하되 숫자는 확정 표기하지 않는다.

**막힌 지점**: 실제 5,764자 프롬프트를 VM에 올리려는 중 `scp`가 stdin을 못 받아 base64
우회(109KB)를 준비하다 중단됨. 재개하면 §7 방법(검색 미리 수행 + 동시 6건)과 동일 스크립트로
맞춰 재는 것을 권한다 — 지금 결과는 그 스크립트가 아니라서 §1과 열 대 열로 비교하기엔
방법이 다르다.

### 재측정 — 실제 프롬프트·실제 다양성으로 (2026-08-04, vLLM Qwen3 **14B** AWQ)

위 "막힌 지점"을 다른 경로로 풀었다 — `scp` 대신 **Cloud Shell에 이미 있는 리포·백엔드
venv에서 `build_chat_prompt()`를 직접 호출**해 JSON으로 떨어뜨리고, 그 파일을 VM으로
옮겼다(base64 불필요). 이번엔 **5작물 전부 다른 근거·다른 질문** 6건을 동시에 던졌다
(사과 2건 포함, 프롬프트 3,664~5,132자 — §11 원래 목표였던 5,764자 대역에 실제로 들어온다).

    항목              Ollama(§1)   vLLM 8B(잘린 프롬프트, 위)   vLLM **14B**(실제 프롬프트, 이번)
    동시 6건 첫토큰    4.5→40.2s    0.53~2.52s                2.07~5.64s
    동시 6건 전체 완료 47.0s        6.47s                     13.5s
    prefix cache 히트  기능 없음     61~88%                    **49~66%(요청군별), 정상상태 ~53%**

**⚠️ 위 예측("결론이 바뀔 가능성은 낮다")은 절반만 맞았다** — 정직하게 갈라 적는다:

- **맞은 부분**: 계단식이 사라진다는 §7 판정은 유지된다. Ollama의 "요청당 +7초"와 비교하면
  이번엔 "요청당 +0.7초"다 — **10배 완만**하다.
- **틀린 부분**: 첫토큰이 정확히 평탄하지는 않다. `2.07 → 3.27 → 4.47 → 4.47 → 5.64 → 5.64`로
  **약한 계단이 실제로 있다.** "계단이 사라진다"가 아니라 "계단이 아주 작아진다"가 정확한
  서술이다. prefix cache도 61~88%가 아니라 **49~66%(대부분 50%대)** 다 — 전 측정은 잘리고
  반복된 프롬프트끼리 내용이 비슷해서 캐시가 과대평가됐다. 이번처럼 작물마다 근거가 완전히
  다르면 **공통 접두어(시스템 프롬프트+few-shot, 프롬프트의 절반가량)만 캐시되고 나머지
  (RAG 근거·질문)는 매번 새로 계산된다** — 구조적으로 그래야 정상이고, 이게 실서비스에 더
  가까운 수치다.

**⚠️ 변수가 두 개 같이 바뀌었다 — 이 표를 "8B vs 14B" 비교로 읽지 말 것.** 왼쪽 vLLM 열은
8B+잘린 프롬프트, 오른쪽은 14B+실제 프롬프트다. "14B라서 느려졌다"인지 "프롬프트가 커져서
느려졌다"인지 이 데이터만으로는 못 가른다. 순수 비교는 바로 아래에서 했다.

**결론**: §7 판정("전환 성공")은 여전히 유효하고 실제 프롬프트로도 재확인됐다. 다만 §1과
직접 비교할 절대 수치("40초 대 6초")로 홍보하듯 쓰면 안 된다 — 실제 체감은 "6번째 유저가
40초 기다림" → "6번째 유저가 5.6초 기다림" 정도가 더 정확한 서술이다.

### 순수 비교 — 8B vs 14B, 완전히 같은 조건 (2026-08-04)

위 표의 "변수 두 개가 같이 바뀐" 문제를 없앴다. **같은 `bench.py`·같은 `bench_payloads.json`**
(5작물 6건, 실제 근거·실제 질문, 프롬프트 3,664~5,132자)으로 모델만 8B ↔ 14B로 바꿔 재측정했다.

    항목              vLLM 8B AWQ         vLLM 14B AWQ        배율
    동시 6건 첫토큰    0.11 ~ 1.92s        2.07 ~ 5.64s        약 3배
    동시 6건 완료(개별) 5.95 ~ 6.92s        11.3 ~ 13.5s        약 2배
    동시 6건 전체 완료  6.92s              13.5s               약 2배
    prefix cache 히트  정상상태 ~65.5%      정상상태 ~53%        (아래 참고)

**파라미터가 1.75배(8B→14B) 느는데 완료시간도 거의 그 비율로 늘었다** — 이상 현상이 아니라
연산량에 비례하는 정상적인 결과다. **8B가 6번째 유저 기준 6.9초, 14B는 13.5초** — 둘 다
Ollama의 40초 계단과는 비교가 안 되게 낫지만, 속도만 보면 8B가 유리하다.

**prefix cache가 8B에서 더 높게 나온 이유**: 절대적인 캐시 키 공간(공유 접두어 크기)은
같은데, 8B가 요청을 더 빨리 처리해 **같은 시간에 더 많은 요청이 겹쳐 지나가면서** 캐시
재사용 기회 자체가 늘어난 것으로 보인다 — 확정은 아니고 [확인 필요]로 남긴다.

**→ 속도만 보면 8B, 품질(§9 위 "실측")은 8B·14B 동률(둘 다 0/3 오류)**이었다. 이 프로젝트의
목표(동시 6명, 첫토큰 지연 최소화)에는 **8B가 더 맞는 선택**으로 기운다 — 14B가 크기값을
못 한다는 뜻은 아니고, 지금 확인된 범위(사실 보존)에서는 추가 파라미터가 응답 속도만
깎아먹고 품질 이득은 안 보였다는 뜻이다. 5작물로 표본을 넓혀야 확정할 수 있다(§9 한계 그대로).

### 네 모델 속도 — 같은 `bench.py`·같은 `bench_payloads.json` (2026-08-04)

    항목               Qwen3 8B AWQ  EXAONE 7.8B AWQ  Gemma 3 12B w4a16  Qwen3 14B AWQ
    동시 6건 첫토큰     1.08~2.95s    0.37~2.40s      2.07~4.30s        2.07~5.64s
    동시 6건 완료(개별) 7.00~7.97s    8.93~11.52s     7.86~10.32s       11.3~13.5s
    동시 6건 전체 완료  **7.97s**     11.52s          10.33s            13.5s
    출력 청크수         143~182       276~401         86~149            (미기록)
    생성 속도           25~36 tok/s   35~42 tok/s     **15~23 tok/s**   (산출 불가)

**⚠️ 8B 열은 재측정치다 — 이전 기록(첫토큰 0.11~1.92s, 전체 6.92s)보다 15% 느리다.**
같은 `bench.py`·같은 페이로드인데 갈렸다. 원인은 **prefix cache 상태 차이로 본다** — 이번엔
서버를 갓 띄운 직후라 캐시가 비어 있었고, 이전 측정은 다른 실행 뒤라 데워져 있었다.
**즉 이 표의 절대값은 ±15% 변동폭을 갖는다** — 모델 간 순위(8B < Gemma < EXAONE < 14B)는
그 폭보다 훨씬 크게 갈리므로 결론은 안 바뀐다. **[확인 필요]** 캐시 상태를 통제한 재측정은
안 했다(순위가 안 바뀌어 우선순위를 낮췄다).

**EXAONE의 tok/s가 8B보다 높은 것은 모델이 빠르다는 뜻이 아니다** — 같은 프롬프트의
`prompt_tokens`가 EXAONE 1530 · Qwen3 1983으로, 한국어 토크나이저 효율이 다르다. 토큰은
모델마다 크기가 다른 단위라 tok/s는 **모델 간 비교 지표가 아니다.** 비교할 것은 완료시간이고,
거기선 8B가 1위다.

**첫토큰이 파라미터 수로 두 계급으로 갈린다.** 7.8~8B(0.1~2.4s)와 12~14B(2.1~5.6s)다.
Gemma 3 12B는 이름과 달리 13B(비전 타워 포함)라 14B 대역에 정확히 들어간다.
**어느 모델도 계단식이 없다** — §7 판정은 네 모델 전부에서 통과한다.

**⚠️ "전체 완료" 열만 보고 순위를 매기면 틀린다 — 출력 길이가 모델마다 다르다.**

- EXAONE의 11.52초는 **276~401청크를 뱉은 결과**다. 느린 게 아니라 수다스럽다(§9의 Ollama
  측정에서도 EXAONE 113~140토큰 vs Qwen3 69~77토큰으로 약 2배였다).
- Gemma의 10.33초가 EXAONE보다 나아 보이지만 **청크는 3분의 1(86~149)** 이다. tok/s로 보면
  Gemma 15~23, EXAONE 35~42로 **Gemma가 절반**이다. 13B + GPTQ 조합의 예상 범위다.

**[확인 필요] 8B·14B 측정 때 청크수를 안 남겼다** — 그래서 선두 후보인 8B의 tok/s를 아직
못 낸다. `bench.py`는 이미 청크를 세고 있으니 §9 "방법론 구멍"의 8B 재측정 때 같이 기록할 것.

**결론에는 영향이 없다** — EXAONE·Gemma 둘 다 §9 품질에서 내려갔고, 속도로 뒤집을 우위도
없다(EXAONE은 첫토큰만 동급, Gemma는 첫토큰이 14B 대역).

## 12. 다음 판단 — 영속화 먼저인가, 정밀 재측정/다른 모델 벤치 먼저인가

**영속화(§8의 3단계, `startup.sh` 반영)를 먼저 하는 것을 권한다.** 이유:

- **휘발 위험이 있는 건 이것뿐이다.** 정밀 재측정(§11 한계)이나 다른 모델 벤치는 VM에
  모델 가중치·pip 캐시가 남아 있는 한 아무 때나 다시 돌릴 수 있다. 반면 지금 떠 있는 vLLM
  프로세스와 그 기동 플래그(`VLLM_USE_FLASHINFER_SAMPLER=0` 등)는 **VM 재부팅·Spot
  재선점 한 번으로 사라진다** — 재현 명령이 사람 손에만 있다.
- **오늘 이 세션에서 같은 패턴을 이미 여러 번 봤다**("설정이 코드에 없어서 조용히
  사라짐" — `infra/ollama-vm/README.md`의 인스턴스 이름 드리프트, 배포 런북에 없던
  ETL 스크립트, 계약 테스트 사각지대 등). vLLM 수동 기동도 정확히 같은 형태다.
- 영속화 자체는 **되돌리기 쉽다** — `startup.sh`에 한 블록 추가일 뿐, `LLM_BACKEND`는
  여전히 `ollama`가 기본값이라(§8) 실서비스는 안 건드린다.

**✅ 실행 명령 확정 (2026-08-04, VM에서 직접 확인)**:

```bash
VLLM_USE_FLASHINFER_SAMPLER=0 \
/home/dohyun0312/vllmenv/bin/vllm serve Qwen/Qwen3-8B-AWQ \
  --port 8000 \
  --max-model-len 8192 \
  --kv-cache-memory 12446605210 \
  --max-num-seqs 8 \
  --served-model-name qwen3-8b
```

venv: `vllm==0.26.0`, Python 3.10.12(`~/vllmenv`).

**⚠️ 위 명령에는 `nohup`/`setsid`가 없다 — 그대로 SSH로 띄우면 세션이 끊길 때 같이 죽는다.**
`gcloud compute ssh $VM --zone=$ZONE -- '...&'` 형태로 백그라운드에 넣어도 SIGHUP을 받는다.
실제로 쓸 때는 이렇게 감싼다(EXAONE 기동 시 확정한 형태):

```bash
VLLM_USE_FLASHINFER_SAMPLER=0 setsid nohup \
  /home/dohyun0312/vllmenv/bin/vllm serve <모델> \
  --port 8000 --max-model-len 8192 --kv-cache-memory 12446605210 \
  --max-num-seqs 8 --served-model-name <이름> \
  < /dev/null > ~/vllm_serve_<이름>.log 2>&1 &
```

`--kv-cache-memory`를 모델이 바뀌어도 **같은 값으로 유지**하면 §11 속도 비교가 공정해진다
(KV 예산이 같아짐). EXAONE 측정도 이 값 그대로 했다.
**EXAONE 계열은 여기에 `--trust-remote-code`를 추가로 붙여야 한다**(§2).

**§11이 EXAONE이 아니라 Qwen3로 쟀다는 뜻이다** — §9의 잠정 결론(충실성·라이선스에서
Qwen3 유리)이 이미 실행에 반영돼 있었다. §9 잠정 결론과 실제 벤치 대상이 일치한다.

**주의할 것 셋**:
- `--kv-cache-memory`를 **바이트로 직접** 줬다(≈11.6GiB) — §3·§5가 권장한
  `--gpu-memory-utilization` 비율 방식이 아니다. §3 표는 EXAONE 아키텍처 기준이라
  Qwen3(다른 레이어·헤드 구성)엔 그대로 안 맞으므로 이 값이 어떻게 도출됐는지는
  **[확인 필요]**로 남긴다 — 그대로 재사용은 되지만 근거는 비어 있다.
- `--served-model-name qwen3-8b` — `VllmClient`가 보내는 `model` 필드가 **이 이름과
  정확히 일치**해야 한다(`Qwen/Qwen3-8B-AWQ`를 그대로 넣으면 모델을 못 찾는다).
  전환 시 `settings.llm_model`을 `qwen3-8b`로 맞출 것.
- venv 설치 커맨드(`pip install` 원문)는 **기록이 없어 재현 미확인**이다 — 신규 VM에
  옮길 때는 이 지점부터 검증할 것.

**`startup.sh`는 아직 안 건드렸다** — 지금부터 다른 모델로 바꿔가며 벤치하면 이 프로세스
자체가 사라지므로, 그 전에 이 조합을 문서에 박아뒀다(§8 표 갱신 예정). systemd 서비스화는
모델 벤치가 끝나고 최종 모델이 정해진 뒤 한 번에 하는 것이 낫다 — 지금 넣으면 벤치 중
모델을 바꿀 때마다 스크립트를 고쳐야 한다.

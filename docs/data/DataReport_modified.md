## 2. Data-Guideline.md 이행 시 발생하는 구조적 제약 (핵심)

API 문서를 상세 검토한 결과, 가이드라인이 전제한 스키마와 **실제 API의 요청/응답 스펙이 다른 지점**이
여러 곳 있다. 이는 접근 권한 문제가 아니라 **API 자체의 설계 한계**이므로, 코드로 우회할 수 없고
가이드라인 자체를 조정해야 한다.

### 2.1 ★가장 중요★ 농경지화학성 통계정보 V2 — 연도별 시계열 조회가 불가능함

`Data-Guideline.md` §4는 "최소 10년치, 가급적 15~20년치"의 `01_soil_chemistry` 시계열 확보를
전제로 한다. 그러나 실제 `getFarmExamPhInfo`/`getFarmExamOmInfo`/`getFarmExamApInfo`의
**요청 파라미터는 `serviceKey`, `STDG_CD` 두 개뿐이고 연도(year) 파라미터가 아예 없다.**
응답에도 조사연도 필드가 없다(`stdg_Cd`, `bjd_Nm`, 면적 구간 필드들뿐). 즉 이 API는 **"현재
시점의 최신 통계 스냅샷 1건"만 제공**하며, 과거 연도를 지정해 시계열을 뽑아내는 기능 자체가
없다.

→ **결론: 이 API로는 지역당 1개 관측점(현재 시점)만 얻을 수 있다. "지역당 4~5개 관측점 확보"
전제는 이 API만으로는 실현 불가능**하다. (참고로 병기용으로 `weather_snapshot` 식 연 단위
백필이 필요하다면, 이 API가 아니라 별도의 과거연도별 통계 데이터셋이 있는지 data.go.kr에서
추가로 찾아야 하며, 현재 발급된 7개 키 범위에는 없다.)

### 2.2 농경지화학성 값이 "평균값"이 아니라 "면적 구간 분포"로 제공됨

`Data-Guideline.md` §2-1은 `pH 평균`, `유기물 평균(g/kg)`, `유효인산 평균(mg/kg)`을 단일
숫자 필드로 가정했다. 그러나 실제 응답은 이런 평균값이 아니라, **지목(논/밭/시설/과수) ×
농도구간(6단계)의 "면적(ha)" 조합 — pH 기준 24개 컬럼(`acid_Rfld1_Area`~`acid_Fruit6_Area`)**
으로 온다. 유기물·유효인산도 동일한 구조(지목×구간별 면적).

→ **결론: `01_soil_chemistry.csv`의 `pH`, `organic_matter`, `available_p` 컬럼을 채우려면
구간 중앙값 기반 가중평균을 직접 계산해야 하며, 이는 실측 평균이 아니라 근사치**다(구간이
넓을수록 오차 커짐, 특히 "6.6 이상"/"51 이상" 같은 개방형 상한 구간은 중앙값 추정이 더 부정확).
이 근사 방법론을 데이터에 명시적으로 표기해야 한다(예: `pH_estimated=true` 플래그, 혹은 원본
구간 면적 자체를 보조 컬럼으로 함께 저장).

### 2.3 토양도 기반 토양특성 단면정보 V2 — 지역 단위 조회가 불가능, PNU(필지) 단위만 가능

`Data-Guideline.md` §2-3은 `region_code`(법정동 10자리)로 심토토성/자갈함량/경사도를 조회
가능하다고 전제했다. 그러나 실제 `getSoilCharacterSctnn`의 **필수 파라미터는 `PNU_CD`(19자리
지번코드)뿐이며 `STDG_CD` 파라미터 자체가 없다.** 즉 이 API는 "이 필지의 토양특성"만 알려주고,
"이 읍면동 전체 필지 목록"을 받아오는 기능이 없다.

→ **결론: `02_soil_physical.csv`를 region_code 단위로 만들려면, 먼저 그 지역에 속한 대표
PNU 코드를 알아야 하는데, 이 API군(7개) 안에는 "지역→PNU 목록" 변환 기능이 없다.**
아래 §2.4와 결합되어 더 큰 문제가 된다.

### 2.4 토양검정 화학성 상세정보 V2(목록 조회)에 PNU 코드가 없고 주소 텍스트만 있음

§2.3의 문제를 우회하는 방법으로 "`getSoilExamList`(법정동 단위 목록 조회)에서 나오는 필지들의
PNU 코드를 얻어 `getSoilCharacterSctnn`에 재사용"하는 방법을 시도했으나, 실제 응답 필드를
보면 `PNU_Nm`(예: `강원특별자치도 강릉시 강동면 모전리 12`, 지번주소 **텍스트**)만 있고
`PNU_Cd`(19자리 코드) 필드는 없다.

→ **결론: 텍스트 주소에서 본번/부번을 파싱하고, 법정동코드(10자리)+산일반구분(1자리)을
조합해 19자리 PNU를 "역산 구성"하는 우회가 가능하긴 하나(예: "모전리 12" → 본번 0012,
부번 0000, 산/일반은 텍스트에 "산"이 없으면 일반=1로 추정), 이는 산/일반 구분을 추정치로
처리하는 것이라 일부 필지에서 조회 실패(404/데이터없음) 가능성이 있다.** 완벽한 방법은 아니고
"최선 시도(best-effort)" 수준의 우회다.

### 2.5 ★블로커★ 전국 법정동코드(읍면동) 목록을 제공하는 API가 7개 중에 없음

`Data-Guideline.md`/`DataPreprocessing.md`가 요구하는 "150개 읍면동 층화표집"을 하려면,
먼저 전국 읍면동(또는 최소 시/군/구) 단위의 **법정동코드 마스터 리스트**가 있어야 조회 대상을
정할 수 있다. 그러나 7개 API 문서 어디에도 "지역 코드 목록 조회" 기능은 없다. 문서에는
"STDG_CD ... * 행안부, 행정표준코드 참조"라고만 적혀 있어, **이 코드 자체는 별도의 행안부/
행정표준코드 시스템(`code.go.kr` 등)에서 구해야 한다는 뜻**이며, 지금 발급된 키로는 접근할
수 없는 별개의 참조 자료다.

→ **다만 API 스펙의 예시값 `STDG_CD=5279000000`을 보면 이 코드가 "전북특별자치도 고창군"
(시군구 단위, 읍면동 자리가 0000으로 채워진 코드)을 가리킨다.** 즉 이 API는 **읍면동 단위뿐
아니라 시/군/구 단위 조회도 지원**한다. 따라서 "150개 읍면동" 대신 **"150개 시/군/구"** 단위로
목표를 낮추면, 코드 마스터 없이도 훨씬 다루기 쉬워진다(전국 시/군/구는 약 250개뿐이라 완전
목록화가 상대적으로 용이함). 그래도 이 코드들을 정확히 확보하는 방법(사용자가 마스터 파일을
제공 / 제가 code.go.kr에서 웹으로 가져오기 / 소수 검증된 코드만 우선 사용)은 **결정이
필요한 지점**이라 3번 항목에서 별도로 질문한다.

### 2.6 기타 사소한 이행 이슈

- 응답 필드명 대소문자가 API마다 제각각이다(`result_Code` vs `Result_Code`, `stn_Cd` vs
  `Obsr_Spot_Code` 등). 파서 작성 시 API별로 분기 처리 필요.
- 농업기상 관측지점은 전국 **218개소뿐**이라(현재 API 응답 `Total_Count=218`), 150개 지역을
  모두 "가장 가까운 관측지점"으로 매핑하면 여러 지역이 같은 관측지점을 공유하게 된다(불가피,
  가이드라인도 이를 전제하고 있어 문제는 아님).
- 농경지화학성 통계 API의 지목 구분(논/밭/시설/과수)과 우리가 필요로 하는 작물(사과·배·오이·
  감자·상추)의 재배 지목이 다르므로(예: 사과·배는 "과수", 오이는 "노지"+"시설" 혼재, 감자는
  "밭", 상추는 "노지"+"시설"), pH/유기물/유효인산 근사 평균을 계산할 때 **어떤 지목 구간을
  기준으로 삼을지 결정이 필요**하다(전체 지목 합산 vs 작물별 주요 지목만 사용).

## 3. 결정이 필요한 사항 (사용자 확인 요청)

위 §2.5(법정동코드 마스터 소스)가 150개 지역 선정 작업의 실질적 블로커다. 아래 중 어떤 방식으로
진행할지 확인 후 다음 단계(150개 지역 선정 + 4개 CSV 생성)를 진행하겠다.

1. **사용자가 법정동코드(또는 시/군/구 코드) 마스터 목록을 직접 제공** — 가장 정확하고 빠름.
2. **제가 code.go.kr(행정표준코드관리시스템) 등 공개 웹 자료를 가져와 코드 목록을 구성** — 추가
   조사 필요, 시간 소요.
3. **"읍면동" 대신 "시/군/구"(전국 약 250개) 단위로 스코프를 낮추고, 일반 지식으로 후보 코드를
   구성한 뒤 API 응답의 `bjd_Nm`(법정동명 에코백)으로 하나하나 실시간 검증하며 150개를 확정** —
   외부 자료 없이 진행 가능하지만 다소 비효율적이고 실패(오탐지) 사례가 발생할 수 있음.

# 논문 도메인 지식 수집 루프 — 아키텍처 개요

## 왜 이렇게 짜는가

지금까지 사람이 직접 했던 작업 흐름은:

```
검색 → 논문 원문 읽기 → 8단계 템플릿으로 정리 → 정리본에서 "보완" 항목(gap) 확인
→ 그 gap을 다음 검색 키워드로 → 반복
```

이걸 Claude Code에서 자동 루프로 돌리려면 반드시 막아야 할 실패 모드가 하나 있습니다:
**오케스트레이터(메인 스레드)가 매 반복마다 과거에 정리한 논문 노트 전체를 다시 읽어 들이는 것.**
논문 노트가 10편, 20편 쌓이면 이것만으로 컨텍스트가 터지고 비용이 기하급수적으로 늘어납니다.

그래서 이 시스템은 **"명세서(registry) 파일"** 하나를 중심에 둡니다. 이 파일은:
- DB.md의 `crop_growth_guide`, `soil_change_rule` 스키마를 기준으로 "무엇이 채워졌고 무엇이 비어있는지"를 **표 형태로 압축**해서만 담습니다.
- 논문 원문이나 정리본 본문은 절대 이 파일에 들어가지 않습니다 — 파일 경로와 1줄 요약만 인덱싱합니다.
- 오케스트레이터는 매 루프마다 이 파일 하나(수 KB 수준)만 읽고 다음 행동을 결정합니다.

무거운 작업(웹 검색, PDF 원문 읽기, 8단계 정리본 작성)은 전부 **서브에이전트**에게 위임합니다.
Claude Code의 서브에이전트는 자기만의 독립된 컨텍스트 창에서 실행되고, 부모(오케스트레이터)에게는
**작업 결과 요약만** 반환합니다. 즉 논문 원문 전체가 서브에이전트 안에서만 소비되고, 오케스트레이터
컨텍스트로는 절대 넘어오지 않습니다. 이것이 이 아키텍처의 토큰 절약 핵심 메커니즘입니다.

## 구성 요소

```
knowledge-base/
  registry.md            ← 명세서(핵심). 오케스트레이터가 매번 읽는 유일한 상태 파일
  search-log.md           ← 이미 시도한 검색 쿼리 기록 (중복 검색 방지)
  keyword-queue.md        ← 다음에 검색할 키워드 우선순위 큐
  papers/
    apple/               ← 작물별 폴더
      <slug>.md           ← 개별 논문 8단계 정리본 (전체 텍스트, 평소엔 안 읽음)
    pear/
      <slug>.md

.claude/
  agents/
    scout.md              ← 서브에이전트 1: 논문 탐색(검색만, 원문 안 읽음)
    extractor.md           ← 서브에이전트 2: 원문 읽고 8단계 정리본 작성 + delta 반환
    registry-keeper.md     ← 서브에이전트 3: registry.md/큐/로그 갱신 + gap 재계산
  commands/
    research-loop.md       ← 오케스트레이터 슬래시 커맨드. /research-loop 로 루프 실행
```

## 루프 한 사이클의 흐름

1. **오케스트레이터**가 `knowledge-base/registry.md`와 `keyword-queue.md`만 읽는다(둘 다 수 KB).
2. 큐에서 우선순위 최상단 키워드를 뽑아 **`scout` 서브에이전트**를 호출한다.
   - `scout`은 Aira MCP(`aira-semanticscholar`, Semantic Scholar + arXiv 기반)로 검색하고,
     `search-log.md`와 대조해 이미 본 논문을 걸러낸 뒤,
     후보 논문 3~5편의 **메타데이터(제목/출처/DOI/한 줄 관련성)만** 오케스트레이터에 반환한다.
   - 원문은 이 단계에서 열어보지 않는다(검색 결과 스니펫만으로 관련성 판단).
3. 오케스트레이터가 후보 중 채택할 논문을 정하고(보통 스니펫만으로 사람 대신 판단), 논문별로
   **`extractor` 서브에이전트**를 병렬 또는 순차 호출한다.
   - `extractor`는 그 논문 원문만 읽고, `knowledge-base/papers/<crop>/<slug>.md`에 8단계 정리본을 쓴 뒤
     오케스트레이터에는 **compact delta**(YAML 몇 줄: 다룬 crop/indicator/action_type, 커버리지 상태,
     새로 발견된 gap 키워드)만 반환한다. 정리본 본문 자체는 반환하지 않는다.
4. 오케스트레이터가 delta들을 모아 **`registry-keeper` 서브에이전트**를 호출한다.
   - 이 에이전트가 `registry.md`, `keyword-queue.md`, `search-log.md`를 갱신한다.
   - 이때도 과거 논문 정리본 전체를 다시 읽지 않고, delta + 현재 registry.md(작음)만 가지고 갱신한다.
5. 오케스트레이터는 갱신된 registry.md를 보고 **정지 조건**을 확인한다(아래 참고). 아니면 2번으로 복귀.

## 정지 조건 (무한 루프 방지)

`research-loop.md`에 명시하지만 요약하면:
- `crop_growth_guide` 핵심 지표(사과·배·오이·감자·상추 × ph/ec/p2o5/organic/temp 계열)가 전부
  "filled" 또는 "partial" 이상이 되면 정지.
- 또는 최대 반복 횟수(기본 15회) 도달 시 정지.
- 또는 한 사이클 동안 채택된 신규 논문이 0편이면(더 못 찾음) 정지하고 사람에게 보고.
- **또는 사용자가 대화 중 "멈춰"라고 말하면 그 즉시 정지.** 진행 중이던 사이클을 억지로
  끝까지 돌리지 않고, 서브에이전트 호출 사이 지점에서 바로 중단하고 그때까지의 진행
  요약을 보고한다(`research-loop.md`의 "중단 처리" 섹션 참고).

## 언어별 검색 도구 분리

`scout`은 검색 대상 언어에 따라 도구를 나눠 씁니다:
- **한국어 키워드** → `WebSearch`(일반 웹서치)로 검색. KCI·학위논문·농촌진흥청 자료 등
  국내 문헌은 Aira(Semantic Scholar 기반)로는 거의 안 잡히기 때문입니다.
- **영어 키워드** → Aira MCP(`aira-semanticscholar`)로 검색.

이 구분은 `scout.md`에 명시되어 있으며, 대부분의 국내 대상 작물(사과·배·오이·감자·상추)
문헌은 한국어 검색 경로로 찾게 될 가능성이 높습니다.

## git에 대하여

이 루프는 **git과 전혀 상호작용하지 않습니다.** 서브에이전트 중 어느 것도 git 명령을
실행할 수 있는 tool을 부여받지 않았고, 오케스트레이터 지침에도 git 사용 금지가 명시되어
있습니다. `knowledge-base/` 아래 파일들을 커밋할지, 언제 할지는 전적으로 사람이 별도로
판단해서 직접 수행하십시오.

## 사용 방법 (요약)

1. 이 폴더 전체를 프로젝트 루트(예: `foryourfarm/` 리포지토리)에 복사한다.
2. Aira MCP(`aira-semanticscholar`, https://github.com/hamid-vakilzadeh/AIRA-SemanticScholar)를
   Claude Code에 연결하고, `scout.md`/`extractor.md`의 `tools` 항목을 실제 도구 이름으로
   맞춰 넣는다(지금은 README 기능 설명 기반 추정치이므로, 연결 후 도구 목록으로 반드시
   재확인할 것). Aira는 Semantic Scholar API + arXiv 전문 다운로드 기반이라 **국내 학술지
   (KCI 등) 원문 확보는 취약할 수 있음** — 그래서 한국어 검색은 별도로 `WebSearch`를
   쓰도록 이미 분리해뒀고, 그래도 원문을 못 구하면 사용자가 PDF를 직접 업로드하는 경로와
   병행하는 것을 권장한다.
3. `knowledge-base/registry.md`의 초기 시드(이 폴더에 기본 템플릿 포함)를 프로젝트의 실제
   DB.md 스키마에 맞게 한 번 검토한다.
4. Claude Code에서 `/research-loop` 실행. 도중에 멈추고 싶으면 언제든 "멈춰"라고 입력한다.
